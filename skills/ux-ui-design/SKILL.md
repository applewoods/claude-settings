# UX/UI 디자인 매뉴얼

> **팀으로 진행:** 여러 단계이거나 검증이 중요한 일은 `team-orchestration` 스킬의 "UX/UI 디자인" 팀 구성(scout·builder·expert·verifier)으로 나눠 맡긴다. 각 팀원은 이 매뉴얼을 따른다.

이 매뉴얼은 **순서·판단 기준·완료 기준**을 정한다. 깊은 내용은 아래 참고 문서에 있고, 표의 "언제"에 해당할 때만 읽는다.

## 0. 깊이부터 정한다
같은 화면이라도 쓰임에 따라 필요한 절차가 다르다. 시작할 때 셋 중 하나로 정하고, 모르면 묻는다.

| 단계 | 예 | 반드시 | 생략 가능 |
|---|---|---|---|
| **연구 데모** | 논문 시연, 실험용 UI, 일회성 발표 | `DESIGN.md` 최소판(색·글꼴·간격), 핵심 흐름 1개, 로딩·오류 상태, 대비·키보드 | IA 문서, 온보딩, 다크 모드, 사용성 테스트, 화면 명세 |
| **내부 도구** | 연구실·팀 대시보드, 관리 화면 | 위 + 빈 상태, 표·필터 기준, 파괴적 작업 확인/되돌리기, 휴리스틱 평가 | 랜딩 수준의 시각 완성도, 공식 접근성 검토 |
| **출시 서비스** | 외부 사용자가 쓰는 웹·앱 | 아래 전 단계 + 접근성 검토 + 짧은 사용성 테스트 + 화면 명세 | 없음(생략 시 이유를 보고) |

## 1. 흐름과 구조를 먼저 본다 (화면을 그리기 전)
- 기획 문서(`service-planning` 산출물)가 있으면 읽고, 핵심 과업 1~3개를 "누가, 무엇을 끝내려고" 한 줄로 적는다. 화면은 과업을 위해 존재한다.
- 과업마다 **행복 경로 + 실패 경로**(입력 오류, 권한 없음, 데이터 없음, 네트워크 끊김)를 흐름으로 적는다. 실패 경로가 빠진 흐름은 미완성이다.
- 메뉴·내비게이션은 기능 목록이 아니라 사용자가 찾는 말로 묶는다.
- **언제 읽나:** 화면이 5개 이상이거나 메뉴 구조를 새로 잡을 때 → `references/ia-flows.md`

## 2. 기준을 만든다: `docs/DESIGN.md`
- 프로젝트에 `docs/DESIGN.md`가 없으면 디자인 작업 전에 먼저 만든다. 양식은 `templates/DESIGN.md`(토큰 계층: 원시 → 의미 → 컴포넌트).
- 분위기·다크 모드·참고 서비스를 나에게 묻는다(질문 3개 이내). 정해진 게 없으면 추천안으로 초안을 만들고 `[가정]`으로 표시한다.
- 참고 서비스가 있으면 [VoltAgent/awesome-claude-design](https://github.com/VoltAgent/awesome-claude-design)의 DESIGN.md 중 하나를 골라 **내 색·글꼴로 바꿔서** 쓴다. 구조만 참고하고 그대로 베끼지 않으며, 로고·고유 그래픽은 쓰지 않는다.
- 정한 값은 Tailwind 테마(CSS 변수)에 그대로 옮긴다. **화면 코드는 의미 토큰(`--color-danger`, `--space-4`)과 그것을 참조하는 컴포넌트 토큰만 쓰고**, 원시 토큰·원시값(`gray-600`, `#E5484D`, `13px`)을 직접 쓰지 않는다.
- 판단 기준:
  - 색은 역할로 정한다: 배경·표면·글자(본문/보조)·테두리·강조(primary) 1개·상태색(성공/경고/위험/정보). 강조색이 2개 이상이면 무엇이 중요한지 흐려진다.
  - 간격은 4 또는 8 배수 한 가지 단위, 글자 크기는 5~7단계. 그 밖의 값이 필요하면 토큰을 추가하고 화면에 임의값을 넣지 않는다.
  - 상태색만으로 의미를 전달하지 않는다(아이콘·문구 병행).

## 3. 화면 종류에 따라 스킬을 고른다
| 화면 | 쓸 것 |
|---|---|
| **랜딩·소개·마케팅 페이지** (공개 웹페이지) | `design-taste-frontend` 스킬의 절차를 따른다(방향 고르기 → 문구 → 제작 → 검사 스크립트 → 스크린샷 비평). |
| **앱 화면** (로그인 후 화면, 대시보드, 폼, 설정, 모바일 앱) | `frontend` 스킬 + shadcn/ui + `docs/DESIGN.md`. `design-taste-frontend`는 앱 화면용이 아니므로 쓰지 않는다. |

- 둘이 충돌하면 이렇게 정리한다: `design-taste-frontend`는 카드·얇은 테두리·그림자·둥근 모서리를 금지하지만, 앱 화면에서는 shadcn/ui 기본 컴포넌트를 쓴다. 같은 서비스 안에서 랜딩과 앱의 **색·글꼴은 `DESIGN.md`로 통일**하고, 구성 방식만 다르게 간다.
- 참고 스크린샷을 주면 구조와 기준을 참고해 만든다. 디자인을 그대로 복제하지 않는다.
- 시안은 HTML 목업 → 바로 코드. Figma는 내가 요청할 때만 쓴다.

## 4. 화면을 설계할 때 확인할 것
화면마다 아래를 정한 뒤 만든다. 해당할 때 참고 문서를 읽는다.

| 언제 | 판단 기준(요약) | 참고 |
|---|---|---|
| 데이터를 불러오거나 저장하는 모든 화면 | 빈·로딩·오류·부분 실패·권한 없음 상태를 각각 설계(연구 데모는 로딩·오류만). 파괴적 작업은 "확인 창"보다 **되돌리기**를 우선 | `references/interaction-states.md` |
| 폼, 입력, 가입·온보딩 | 형식 오류는 칸을 떠날 때, 누락은 제출 때 필드 옆에 + 고치는 방법. 입력한 값은 절대 지우지 않음 | `references/interaction-states.md` |
| 모바일 웹·앱 | 주요 행동은 엄지가 닿는 하단, 제스처에는 버튼 대안, iOS/Android 관례를 섞지 않음 | `references/mobile-ux.md` |
| 모든 화면(출시 서비스는 필수 정독) | WCAG 2.2 AA 핵심 기준과 흔한 위반 | `references/accessibility.md` |
| 버튼·안내·오류·빈 상태 문구 | 무엇이 일어났는지 + 어떻게 하면 되는지. 버튼은 동사로 결과를 말함 | `references/ux-writing-ko.md` |
| 표·대시보드·관리 화면 | 숫자는 오른쪽 정렬·고정폭 숫자, 첫 화면은 "지금 행동할 것" 위주 | `references/data-dense.md` |
| AI가 생성·추천·요약하는 기능 | 불확실성·근거 표시, 사용자가 고치고 되돌릴 수 있게, 실패 시 대안 경로 | `references/ai-ux.md` |
| 개발자(또는 다른 세션)에게 넘길 때 | 상태별 화면·토큰·반응형 규칙·문구를 한 문서로 | `templates/screen-spec.md` |

## 5. 눈으로 확인한다
- 만든 화면은 내장 브라우저로 열어 **모바일 폭(375~390px)과 데스크톱 폭**에서 확인한다. 바꾼 뒤 다시 본다.
- 정상 데이터만 보지 말고 **빈 데이터(연구 데모는 생략 가능), 아주 긴 텍스트(한국어 긴 이름·영문 긴 단어), 오류 응답, 느린 네트워크**를 한 번씩 띄워 본다.
- 키보드(Tab)만으로 핵심 과업을 끝까지 해 본다.

## 6. 배포 전 점검
1. `web-design-guidelines`로 바꾼 화면 코드를 검사한다(접근성, 포커스, 폼, 애니메이션, 터치).
2. `design:design-critique`로 스크린샷을 놓고 디자인을 검토하고, 지적된 상위 3개를 고친다.
3. 한국어 문구(버튼, 안내, 오류 메시지)는 `design:ux-copy`로 다듬는다. 오류 메시지에는 해결 방법을 함께 쓴다.
4. 출시 서비스라면 `design:accessibility-review`로 한 번 더 본다.
5. 내부 도구·출시 서비스는 휴리스틱 평가를, 출시 서비스는 실제 사용자 3~5명의 짧은 사용성 테스트를 한다 → `references/usability-review.md`. 사용자를 구할 수 없어 Claude가 대리 점검만 했다면 "사용성 테스트 미실시"로 보고한다.

## 기본값 (내가 따로 정하지 않았을 때)
- 접근성: 글자 대비 4.5:1 이상(큰 글자 포함), 터치 영역 44px 이상, 키보드로 조작 가능, 포커스 표시 유지. 추가로 입력칸 테두리·아이콘 등 UI 요소 3:1. 4.5:1(모든 글자)과 44px는 WCAG AA 최소(큰 글자 3:1, 대상 24px)보다 엄격한 이 프로젝트 기본값이며, 낮추려면 나에게 묻는다.
- 다크 모드: 프로젝트마다 `DESIGN.md`에서 정한다. 정하지 않았으면 라이트만 만들고, 색은 의미 토큰(CSS 변수)으로 둬서 나중에 추가하기 쉽게 한다.
- 시안 도구: HTML 목업 → 바로 코드. Figma는 내가 요청할 때만 쓴다.
- 움직임: 200~300ms 안팎, 의미 있는 전환에만. `prefers-reduced-motion`이면 끈다.

## 흔한 실수 (바로 고칠 것)
- 정상 데이터 화면만 만들고 로딩·오류 상태가 없음(내부 도구·출시 서비스는 빈 상태도).
- 회색 보조 글자가 대비 미달(흰 배경의 연회색 placeholder를 라벨 대신 사용).
- 아이콘만 있는 버튼에 이름(aria-label)이 없음, 포커스 테두리를 `outline: none`으로 지움.
- 화면마다 다른 간격·색 임의값, 강조색 남발, 모든 것을 카드로 감쌈(앱 화면 포함).
- "오류가 발생했습니다"처럼 원인·해결이 없는 문구, "확인/취소"처럼 결과를 말하지 않는 버튼.
- AI 결과를 사실처럼 단정해서 보여 주고, 고치거나 되돌릴 방법이 없음.

## 완료 기준
- [ ] 0단계의 깊이(연구 데모/내부 도구/출시 서비스)를 정했고, 생략한 절차를 보고에 적었다.
- [ ] 핵심 과업의 행복 경로와 실패 경로가 화면에 반영됐다(연구 데모는 시연할 핵심 흐름 1개).
- [ ] `docs/DESIGN.md`가 있고, 화면 코드가 그 의미·컴포넌트 토큰(테마 변수)만 쓰고 원시값을 직접 쓰지 않는다.
- [ ] 화면 종류에 맞는 스킬을 썼다(랜딩은 `design-taste-frontend`, 앱 화면은 `frontend`).
- [ ] 데이터가 있는 화면마다 로딩·오류 상태가 있다(내부 도구·출시 서비스는 빈 상태까지).
- [ ] 모바일 폭과 데스크톱 폭에서 직접 열어 봤고, 키보드만으로 핵심 과업을 끝냈다.
- [ ] `web-design-guidelines` 검사에서 나온 지적을 고쳤거나, 고치지 않은 이유를 보고했다.
- [ ] 디자인 검토에서 나온 상위 문제를 고쳤다.
- [ ] (출시 서비스) 접근성 검토와 사용성 테스트 결과를 보고했다(대리 점검만 했으면 미실시로 명시).
