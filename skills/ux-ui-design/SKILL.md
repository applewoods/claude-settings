# UX/UI 디자인 매뉴얼

전문 지식은 다른 스킬에 맡기고, 이 매뉴얼은 **순서와 연결**만 정한다.

## 1. 기준부터 만든다: `docs/DESIGN.md`
- 프로젝트에 `docs/DESIGN.md`가 없으면 디자인 작업 전에 먼저 만든다.
- 분위기·다크 모드·참고 서비스를 나에게 묻는다(질문 3개 이내). 정해진 게 없으면 추천안으로 초안을 만들고 `[가정]`으로 표시한다.
- 참고 서비스가 있으면 [VoltAgent/awesome-claude-design](https://github.com/VoltAgent/awesome-claude-design)의 DESIGN.md 중 하나를 골라 **내 색·글꼴로 바꿔서** 쓴다. 그대로 베끼지 않고, 로고·고유 그래픽은 쓰지 않는다.
- 담을 내용: 색(배경·글자·강조·상태색), 글꼴과 크기 단계, 간격 단위, 모서리 둥글기, 그림자 사용 여부, 다크 모드, 문구 톤.
- 정한 값은 Tailwind 테마(CSS 변수)에 그대로 옮긴다. 화면 코드에서는 이 값만 쓴다.

## 2. 화면 종류에 따라 스킬을 고른다
| 화면 | 쓸 것 |
|---|---|
| **랜딩·소개·마케팅 페이지** (공개 웹페이지) | `design-taste-frontend` 스킬의 절차를 따른다(방향 고르기 → 문구 → 제작 → 검사 스크립트 → 스크린샷 비평). |
| **앱 화면** (로그인 후 화면, 대시보드, 폼, 설정, 모바일 앱) | `frontend` 스킬 + shadcn/ui + `docs/DESIGN.md`. `design-taste-frontend`는 앱 화면용이 아니므로 쓰지 않는다. |

- 둘이 충돌하면 이렇게 정리한다: `design-taste-frontend`는 카드·얇은 테두리·그림자·둥근 모서리를 금지하지만, 앱 화면에서는 shadcn/ui 기본 컴포넌트를 쓴다. 같은 서비스 안에서 랜딩과 앱의 **색·글꼴은 `DESIGN.md`로 통일**하고, 구성 방식만 다르게 간다.
- 참고 스크린샷을 주면 구조와 기준을 참고해 만든다. 디자인을 그대로 복제하지 않는다.

## 3. 눈으로 확인한다
- 만든 화면은 내장 브라우저로 열어 모바일 폭(375~390px)과 데스크톱 폭에서 확인한다. 바꾼 뒤 다시 본다.

## 4. 배포 전 점검
1. `web-design-guidelines`로 바꾼 화면 코드를 검사한다(접근성, 포커스, 폼, 애니메이션, 터치).
2. `design:design-critique`로 스크린샷을 놓고 디자인을 검토하고, 지적된 상위 3개를 고친다.
3. 한국어 문구(버튼, 안내, 오류 메시지)는 `design:ux-copy`로 다듬는다. 오류 메시지에는 해결 방법을 함께 쓴다.
4. 출시 서비스라면 `design:accessibility-review`로 한 번 더 본다.

## 기본값 (내가 따로 정하지 않았을 때)
- 접근성: 글자 대비 4.5:1 이상, 터치 영역 44px 이상, 키보드로 조작 가능, 포커스 표시 유지.
- 다크 모드: 프로젝트마다 `DESIGN.md`에서 정한다. 정하지 않았으면 라이트만 만들고, 색은 CSS 변수로 둬서 나중에 추가하기 쉽게 한다.
- 시안 도구: HTML 목업 → 바로 코드. Figma는 내가 요청할 때만 쓴다.

## 완료 기준
- [ ] `docs/DESIGN.md`가 있고, 화면 코드가 그 값(테마 변수)만 쓴다.
- [ ] 화면 종류에 맞는 스킬을 썼다(랜딩은 `design-taste-frontend`, 앱 화면은 `frontend`).
- [ ] 모바일 폭과 데스크톱 폭에서 직접 열어 봤다.
- [ ] `web-design-guidelines` 검사에서 나온 지적을 고쳤거나, 고치지 않은 이유를 보고했다.
- [ ] 디자인 검토에서 나온 상위 문제를 고쳤다.
