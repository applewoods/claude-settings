# 사용성 평가 — 휴리스틱 평가와 짧은 사용성 테스트

**언제 읽나:** 내부 도구·출시 서비스의 배포 전, 또는 "쓰기 불편하다"는 피드백을 받았을 때.
**연구 데모:** 생략 가능. 발표 전 동료 1명에게 핵심 과업을 시켜 보는 것만으로 충분하다.
**역할 분담:** `design:design-critique`는 시각·구성 비평, 이 문서는 과업 수행 관점. 둘은 대체 관계가 아니다.

## 1. 휴리스틱 평가 (Nielsen 10가지 기준, https://www.nngroup.com/articles/ten-usability-heuristics/)
화면을 핵심 과업 순서대로 진행하며 각 기준에 걸리는 문제를 적는다. 가능하면 평가자 2명 이상이 따로 보고 합친다(한 사람은 문제의 일부만 찾는다).

| # | 기준 | 이 화면에서 확인할 질문 |
|---|---|---|
| 1 | 시스템 상태의 가시성 | 지금 무슨 일이 일어나는지(저장 중, 필터 적용 중, 어느 단계) 보이는가 |
| 2 | 현실 세계와의 일치 | 사용자의 말과 순서를 쓰는가(개발 용어·DB 이름 없음) |
| 3 | 사용자 통제와 자유 | 실수로 들어간 곳에서 쉽게 나오고, 되돌릴 수 있는가 |
| 4 | 일관성과 표준 | 같은 행동이 같은 모양·같은 말인가, 플랫폼 관례를 따르는가 |
| 5 | 오류 예방 | 실수할 여지를 처음부터 줄였는가(제약, 기본값, 확인) |
| 6 | 기억보다 인식 | 앞 화면의 정보를 기억해야 하는가, 선택지가 보이는가 |
| 7 | 유연성과 효율 | 숙련자를 위한 단축키·일괄 작업·최근 항목이 있는가 |
| 8 | 미학적이고 간결한 디자인 | 과업과 무관한 정보가 주의를 빼앗지 않는가 |
| 9 | 오류 인식·진단·복구 | 오류 문구가 원인과 해결을 사용자 말로 알려 주는가 |
| 10 | 도움말과 문서 | 필요한 순간 맥락 안에서 도움을 찾을 수 있는가 |

**심각도** (0~4, 출처: https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/): 0 문제 아님 / 1 미관상(여유 있을 때) / 2 작음(낮은 우선순위) / 3 큼(높은 우선순위) / 4 치명(출시 전 반드시 고침). 출시 서비스에서 3은 출시 전에 고치는 것을 이 매뉴얼의 기본으로 한다.
심각도 판단 요소: 빈도, 영향(넘어가기 얼마나 어려운가), 지속성(한 번인가 계속인가), 시장 영향.

보고 형식:
```
[심각도 3] 기준 9 · 업로드 화면 — 20MB 초과 시 "실패"만 표시. 사용자가 원인을 알 수 없음.
제안: 크기 제한을 업로드 전에 표시하고, 오류 문구에 제한과 해결 방법 포함.
```

## 2. 짧은 사용성 테스트 (출시 서비스)
- **인원:** 3~5명이면 반복적으로 나오는 큰 문제는 대부분 드러난다(출처: https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/ — 사용자 행동이 비슷할 때. 뚜렷이 다른 사용자 집단이 여럿이면 집단당 3~4명). 고친 뒤 다시 소수로 반복하는 편이 한 번에 많이 보는 것보다 낫다.
- **대상:** 실제 사용자와 비슷한 사람. 팀원·개발자는 마지막 수단.
- **과업 시나리오 2~4개:** 목표만 주고 방법은 주지 않는다. 화면의 버튼 이름을 시나리오에 쓰지 않는다.
  - 나쁜 예: "'실험 추가' 버튼을 눌러 실험을 만드세요."
  - 좋은 예: "어제 돌린 실험 결과를 팀원과 비교하려고 합니다. 기록해 보세요."
- **진행:** 소리 내어 생각하기를 부탁하고, 막혀도 도와주지 않는다(질문엔 "어떻게 하실 것 같으세요?"로 되묻기). 원격 화면 공유도 충분.
- **기록:** 과업별 성공/도움 받아 성공/실패, 막힌 지점, 사용자가 한 말 그대로.
- **분석:** 2명 이상에게 반복된 문제부터. 사용자의 해결책 제안은 참고만 하고 문제 자체에 집중.
- 실제 사용자 조사 전 가설 정리는 `synthetic-user-research` 스킬을 쓸 수 있다. 단, 가상 페르소나 결과를 사용성 테스트 결과로 보고하지 않는다.

## 3. Claude가 직접 할 수 있는 대리 점검
실제 사용자를 구할 수 없을 때, 내장 브라우저로 처음 보는 사람처럼 과업을 수행하며 휴리스틱 평가를 한다. 이는 휴리스틱 평가의 한 형태일 뿐 사용성 테스트를 대신하지 않는다. 보고에 "대리 점검(실사용자 아님) — 사용성 테스트 미실시"로 명시한다.

## 흔한 실수
- 휴리스틱 평가 결과를 심각도 없이 나열 → 무엇부터 고칠지 모름.
- 테스트 중 사용자를 도와줘서 문제가 가려짐.
- "좋아 보여요" 같은 의견을 성공으로 기록(행동을 봐야 한다).
