# 한국어 UX 라이팅

**언제 읽나:** 버튼·제목·안내·오류·빈 상태·알림 문구를 쓸 때. 다듬기는 `design:ux-copy`로 한다.
**톤 결정:** `docs/DESIGN.md` 6절의 존댓말 수준과 용어집을 따른다. 없으면 **해요체**를 추천안으로 쓰고 `[가정]` 표시.

## 1. 원칙
- **사용자 입장의 결과를 말한다.** 시스템이 무엇을 했는지보다 사용자가 무엇을 얻고 무엇을 하면 되는지.
- **짧게, 하나만.** 한 문장에 한 정보. 버튼은 2~6자 안팎의 동사.
- **같은 것은 같은 말로.** "삭제/제거/지우기"를 섞지 않는다. 용어집에 고정.
- **한 서비스 안에서 어미를 섞지 않는다.** 해요체면 버튼·알림·오류 모두 해요체(버튼 라벨 자체는 명사형·동사 원형 허용: "저장", "저장하기" 중 하나로 통일).
- 개발 용어 금지: "null", "세션 만료", "요청 실패(403)" → 사용자 말로.

## 2. 유형별 공식
| 유형 | 공식 | 나쁜 예 → 좋은 예 |
|---|---|---|
| 버튼 | 결과를 말하는 동사 | "확인" → "저장", "삭제", "초대 보내기" |
| 확인 창 | 제목에 질문+결과, 버튼에 동사 | "정말 하시겠습니까? [확인][취소]" → "프로젝트를 삭제할까요? 30일 안에 휴지통에서 복구할 수 있어요. [삭제][취소]" |
| 오류 | 무엇이 + 왜(알면) + 어떻게 | "오류가 발생했습니다" → "파일이 너무 커서 올리지 못했어요. 20MB 이하로 줄여 다시 올려 주세요." |
| 입력 오류 | 고치는 방법만, 사용자 탓 없이 | "잘못된 입력입니다" → "이메일 주소에 @를 넣어 주세요" |
| 빈 상태 | 무엇이 들어오는지 + 첫 행동 | "데이터가 없습니다" → "아직 실험이 없어요. 첫 실험을 추가해 보세요. [실험 추가]" |
| 성공 | 짧게, 다음 행동이 있으면 함께 | "성공적으로 처리되었습니다" → "저장했어요" / "초대를 보냈어요 · 실행 취소" |
| 로딩 | 오래 걸리면 무엇을 하는지 | "로딩 중..." → "결과 분석 중이에요 (약 30초)" |
| 권한 없음 | 이유 + 방법 | "접근 권한이 없습니다" → "관리자만 볼 수 있어요. 관리자에게 권한을 요청하세요. [권한 요청]" |

## 3. 한국어에서 특히 주의
- **이중 피동·번역투 피하기:** "~되어지다", "~에 의해", "~를 진행하다", "~하는 것이 가능합니다" → "~돼요", "~할 수 있어요".
- **과잉 존대 금지:** "고객님의 요청하신 파일이 준비되셨습니다" → "요청한 파일이 준비됐어요". 사물에 '-시-' 쓰지 않기.
- **부정형보다 긍정형:** "8자 미만은 사용할 수 없습니다" → "8자 이상 입력해 주세요".
- **사과는 시스템 잘못일 때만, 한 번:** 사용자 입력 오류에 "죄송합니다"를 붙이지 않는다.
- **느낌표·이모지 남발 금지.** 오류 문구에는 쓰지 않는다.
- **숫자·단위:** 아라비아 숫자, UI에서는 숫자와 단위를 붙여 쓴다("20MB", "3개", "5분 전"). 날짜 형식은 서비스 안에서 하나로.
- **줄바꿈:** 한국어는 단어 중간에서 끊기기 쉬움 → `word-break: keep-all`(긴 영문·URL은 `overflow-wrap: anywhere` 병행).
- **조사 처리:** 변수가 들어가는 문구("{이름}을/를")는 받침에 따라 조사를 고르는 함수를 쓰거나, 받침과 무관한 구조로 쓴다(예: "{이름} 님을 초대했어요"처럼 '님'을 붙이기, "{파일명} 파일을 삭제했어요"처럼 고정 명사 뒤에 조사 두기).

## 4. 오류 메시지 체크
- [ ] 사용자가 이해하는 말인가(코드·영문 예외 메시지 없음)
- [ ] 무엇이 잘못됐는지 구체적인가
- [ ] 다음에 할 행동이 있는가(버튼 또는 방법)
- [ ] 사용자를 탓하지 않는가
- [ ] 입력한 내용이 보존되는가(문구만큼 중요)
