# 가설 · 실험 설계 · 베이스라인 · 지표 · 타당성 위협

**언제 읽나:** 실험 계획을 세울 때, 베이스라인·데이터셋·지표를 고를 때, 리뷰어 반박을 미리 막을 설계를 점검할 때. 통계 검정 선택·누수 점검·학습 코드는 `data-analysis` 스킬을 따른다.

## §1. 가설과 판정 기준 (실험 전에 적는다)
- 가설 = 기여 문장의 검증 가능한 형태. 예: "H1: 2단계 요약은 단일 단계 대비 사실 일관성 지표 F를 높인다."
- 판정 기준을 미리 고정: 데이터셋 범위, 비교 대상, 주 지표, 시드 수, 통계 비교 방법, 몇 개 조건에서 이겨야 "지지"로 보는지.
- 결과를 본 뒤 지표·데이터셋·비교 대상을 바꾸면 그 사실과 이유를 기록한다(연구 기록의 정직성). 사후에 추가한 분석은 "추가 분석"으로 구분해 보고한다.

## §2. 베이스라인 선정
**구성 (기본)**
| 종류 | 왜 필요 | 예 |
|---|---|---|
| 가장 강한 최신 방법 | 리뷰어가 가장 먼저 찾는다 | 같은 과제 최근 1–2년 SOTA |
| 가장 가까운 선행연구 | 차별점을 실험으로 보임 | 선행연구 지도의 최근접 1–3편 |
| 단순한 방법 | 복잡성이 정당한지 보임 | 규칙 기반, 선형 모델, 잘 튜닝된 표준 모델, (LLM) 단순 프롬프트 |
| 상한·하한 (해당 시) | 개선 여지·의미 해석 | oracle, 무작위, 인간 성능 |
| 우리 방법의 변형 | 구성 요소 기여 | ablation (§4) |

**판단 기준**
- 공정성: 같은 데이터·전처리·튜닝 예산·계산량. 우리 방법만 튜닝하면 리뷰어가 바로 지적한다.
- 재현 vs 인용: 직접 돌리는 것이 원칙. 원 논문 수치를 인용하면 설정이 같은지 확인하고 표에 표시.
- 베이스라인을 못 돌리는 경우(코드 비공개, 비용) 이유를 기록해 본문에 쓸 수 있게.
- LLM 시대 특이점: 범용 대형 모델(프롬프트만)이 특화 방법을 이기는지 반드시 확인한다 — 리뷰어가 가장 많이 묻는다. 비공개 API 모델은 버전·날짜·비용을 기록(재현성 한계).

## §3. 데이터셋과 평가 지표
**데이터셋**
- 주장 범위를 덮도록 고른다: 일반화 주장이면 성격이 다른 데이터 여러 개, 특정 조건 주장이면 그 조건이 드러나는 데이터.
- 표준 벤치마크(비교 가능성) + 주장에 맞는 데이터(타당성)를 함께.
- 사전학습 데이터 오염(테스트셋이 사전학습에 포함) 가능성을 점검 계획에 넣는다.
- 분할: 공식 분할 사용, 없으면 분할 규칙·시드 기록. 데이터 누수 점검은 `data-analysis`.

**지표**
- 주장 ↔ 지표 대응표를 만든다. 주 지표 1–2개를 실험 전에 고정.
| 주장 | 주 지표 | 보조 지표 | 지표의 알려진 한계 |
|---|---|---|---|
- 자동 지표의 한계가 알려진 과제(생성·요약 등)는 인간 평가 또는 LLM 평가자 사용 여부를 정한다. LLM-as-judge를 쓰면 편향(위치·길이·자기 선호) 통제와 인간 평가와의 일치도 확인 계획을 넣는다. 인간 평가는 평가자 수·지침·일치도(예: Krippendorff's α) 계획과 윤리 검토(`ethics-and-data.md`) 여부를 함께.
- 효율 주장 → 시간·메모리·FLOPs·비용. 공정성 주장 → 집단별 지표. 강건성 주장 → 분포 이동 조건.

## §4. ablation과 분석
- 구성 요소마다 "빼면 성능이 떨어진다"를 보일 변형을 계획. 구성 요소가 많으면 핵심 2–3개.
- 민감도: 주요 하이퍼파라미터 변화에 결과가 얼마나 흔들리는가.
- 실패 사례·오류 분석: 정성 예시 + 오류 유형 분포. "언제 안 되는가"는 논의·한계의 재료.
- 통제 실험으로 대안 설명 배제: 파라미터 수·데이터 양·계산량 증가 때문이 아닌가.

## §5. 타당성 위협 (threats to validity)
| 유형 | 질문 | AI 연구의 흔한 위협 | 대응 예 |
|---|---|---|---|
| 내적 | 결과 차이가 정말 우리 방법 때문인가? | 튜닝 예산 불균형, 시드 운, 구현 버그, 데이터 누수 | 동일 예산, 다중 시드+검정, 베이스라인 재현 확인 |
| 구성 | 지표가 측정하려는 개념을 측정하는가? | 자동 지표와 실제 품질 괴리, 벤치마크 지름길(shortcut) | 인간 평가, 대안 지표, 지름길 진단 |
| 외적 | 다른 데이터·모델·언어에도 성립하나? | 단일 데이터셋, 영어만, 특정 모델 크기 | 다양한 데이터·모델, 범위 한정 서술 |
| 결론 | 통계적 결론이 타당한가? | 작은 표본, 다중 비교, 분산 미보고 | 검정·보정·신뢰구간 (`data-analysis`) |

- 각 위협에 대해 **설계로 막는다 / 한계로 밝힌다** 중 하나를 정한다. 둘 다 아니면 리뷰어의 몫이 된다.

## §6. 예상 결과 표 (설계 검증 도구)
- 결과 표를 빈 칸으로 먼저 그린다(행: 방법, 열: 데이터셋×지표). 각 칸에 "주장이 성립하려면 어떤 관계여야 하는지"를 적는다.
- 판단: 이 표가 채워지면 기여가 증명되는가? 빠진 행(베이스라인)·열(데이터·지표)이 없는가? 계산 예산 안에 다 채울 수 있는가(실험 수 × 시드 × 시간)?
- 계산 예산 추정을 일정과 함께 적는다. 모자라면 범위를 줄인다(데이터셋 수보다 시드 수를 먼저 지킨다).

## 흔한 실수
- 결과를 보고 주 지표를 고름.
- 베이스라인을 기본 하이퍼파라미터로만 돌리고 우리 방법만 튜닝.
- 단일 시드 결과로 결론.
- 테스트셋으로 모델·체크포인트 선택.
- 일반화를 주장하면서 데이터셋 하나.
- ablation 없이 "각 구성 요소가 기여한다"고 씀.
