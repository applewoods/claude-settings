# 가상 사용자 사전 조사 매뉴얼

> **팀으로 진행:** `team-orchestration`의 "서비스 기획" 구성을 쓴다. scout가 분포 근거(통계·기존 데이터)를 찾고, builder가 사양·질문을 준비하고, 오케스트레이터가 종합하고, 결과 해석은 Codex 독립 검증(`-t plan`)을 거친다.

근거: Random Silicon Sampling(Sun et al., 2024, arXiv:2402.18144). 집단 분포에서 뽑은 가상 응답자는 **전체 분포**를 꽤 재현하지만, 하위집단을 과장하고, 애매한 집단(무당파)을 못 맞추고, 민감한 주제에서 무해한 답으로 쏠리며, 약 200명 아래에서 불안정했다. 새 서비스 기능은 학습 데이터에 답이 없어 더 불리하다.

## 용도의 선
| 쓴다 | 쓰지 않는다 |
|---|---|
| 사용 시나리오·예외 상황 발굴, 불편함·이탈 이유 찾기, PRD 빈틈 점검, 실제 인터뷰 질문지 다듬기 | 수요 비율 추정("몇 %가 쓴다"), 가격·지불 의사, 기능 우선순위 투표, 논문·투자 자료의 "사용자 조사 결과" |

결과는 모두 **`[가설]`**이다. 실제 사용자로 확인하기 전에는 근거로 쓰지 않는다.

## 절차 (산출물은 프로젝트 `docs/research/`)
1. **서비스 설명** `service.md`: 해결하려는 문제, 대상, 기능 후보 목록. 페르소나에게 보여 줄 내용만 적는다(내부 목표·기대 수치는 빼서 답을 유도하지 않는다).
2. **분포 사양** `persona-spec.json`: 대상 집단을 설명하는 변수 4~7개와 각 분포.
   - 인구통계만 쓰지 말고 **행동 변수**를 넣는다: 현재 쓰는 대안, 문제를 겪는 빈도, 기술 친숙도, 지불 주체 등.
   - **비사용자·잠재 사용자**도 분포에 포함한다(필요를 못 느끼는 사람, 경쟁 서비스 만족자).
   - 분포 근거를 `sources`에 적는다. 근거가 없으면 `[가정]`으로 적고 나에게 확인받는다.
   - 인원: 질적 탐색은 30~50명이 기본. 분포 수치를 보려는 목적이면 200명 이상이어야 하지만, 이 매뉴얼은 그 용도로 쓰지 않는다.
3. **페르소나 생성**:
   ```bash
   python3 ~/claude-settings/skills/synthetic-user-research/scripts/sample_personas.py docs/research/persona-spec.json docs/research/personas.json
   ```
   출력된 인원 분포가 목표 분포와 크게 다르면 seed나 인원을 조정한다.
4. **질문지** `questions.md`: `questions-bank.md`에서 8~12개를 골라 서비스에 맞게 고친다. 과거 행동 → 대안·전환 → 서비스 반응(안 쓸 이유, 2개만 고르기) → 맥락 순서.
5. **인터뷰 실행** (두 모델이 서로의 답을 보지 않고 각각 답한다):
   ```bash
   python3 ~/claude-settings/skills/synthetic-user-research/scripts/persona_interview.py \
     --personas docs/research/personas.json --service docs/research/service.md \
     --questions docs/research/questions.md --out-dir docs/research
   ```
   - 결과: `responses_claude.json`, `responses_codex.json`. 30명 기준 수 분 걸린다(Bash timeout 600000, 길면 백그라운드).
   - 서비스 설명과 질문이 OpenAI·Anthropic으로 전송된다. 미공개 아이디어라 민감하면 먼저 나에게 확인받는다(프로젝트 `CLAUDE.md`의 Codex 설정을 따른다).
6. **종합** `hypotheses.md` (오케스트레이터가 작성):
   - 두 모델의 응답에서 반복되는 패턴을 뽑는다. **두 모델 모두에서 나온 것만 가설로 채택**하고, 한쪽에서만 나온 것은 "약한 신호"로 따로 둔다.
   - 가설마다: 내용 · 근거(페르소나 ID, 모델별 몇 명) · 해당 집단 · 신뢰도(높음/중간/낮음) · 확인 방법.
   - 신뢰도를 낮추는 경우: 한 특성으로만 설명되는 극단적 응답, 애매한 집단(잠재 사용자·비사용자)의 응답, 긍정 일색의 응답.
   - 페르소나가 "좋다/쓰겠다"고 한 것은 근거로 세지 않는다. 불편함·이탈 이유·현재 행동만 센다.
7. **독립 검증**: `codex-verify.sh docs/research - -t plan`으로 종합이 응답 자료와 맞는지, 과장·누락이 없는지 검사한다(브리핑에 응답 파일 경로를 적는다).
8. **실제 확인 계획** `interview-guide.md`: 신뢰도 높은 가설 3~5개를 확인할 **실제 사용자 5명 내외** 인터뷰 질문지와 모집 조건. 결과를 받으면 `hypotheses.md`에 확인/기각을 기록한다.
9. 확인된 내용만 `docs/prd.md`에 반영하고, 확인 전 내용은 `[가설]`로 표시해 둔다.

## 완료 기준
- [ ] 분포 사양에 행동 변수와 비사용자·잠재 사용자가 있고, 분포 근거 또는 `[가정]` 표시가 있다.
- [ ] Claude와 Codex 응답이 모두 있고, 누락된 페르소나가 없다(있으면 이유를 적었다).
- [ ] 가설은 두 모델 공통 패턴만 채택했고, 각 가설에 페르소나 ID·인원·신뢰도가 있다.
- [ ] "좋다/쓰겠다" 응답을 수요 근거로 쓰지 않았다.
- [ ] Codex 독립 검증을 거쳤다.
- [ ] 실제 사용자 확인용 질문지가 있고, 모든 결과가 `[가설]`로 표시돼 있다.
