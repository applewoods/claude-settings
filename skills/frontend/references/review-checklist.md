# 프론트엔드 PR·코드 리뷰 체크리스트

> 쓰는 법: 위에서부터 본다. 위쪽(정확성·보안)에서 문제가 나오면 아래쪽 스타일 지적은 줄인다. 지적에는 등급을 붙인다 — **[필수]** 머지 전 고침, **[권장]** 이번에 고치면 좋음, **[참고]** 취향·다음 기회. 모든 지적에 "왜"를 한 줄.
> 데모 프로젝트는 1~3절만, 출시 서비스는 전부.

## 1. 동작·정확성
- [ ] 직접 실행해 봤나(또는 실행 증거: 스크린샷, E2E 결과). 코드만 읽고 "괜찮다"고 하지 않는다.
- [ ] 로딩·빈·에러·성공 4가지 상태, 그리고 느린 네트워크·중복 클릭·뒤로가기·새로고침.
- [ ] 경쟁 상태: 빠르게 입력·전환할 때 이전 요청 결과가 나중 결과를 덮지 않나.
- [ ] 파생 값을 state로 들고 `useEffect`로 동기화하고 있지 않나.
- [ ] `useEffect` 의존성 배열이 정직한가(린트 경고를 끄지 않았나). 정리 함수(구독·타이머·AbortController)가 있나.
- [ ] 목록 `key`가 안정된 ID인가(index는 순서가 바뀌는 목록에서 상태가 섞인다).
- [ ] 하이드레이션 경고, 콘솔 에러가 없나.

## 2. 보안
- [ ] Server Action·Route Handler 안에서 인증과 **이 리소스에 대한 권한**을 확인하나(proxy만 믿지 않음).
- [ ] 서버 입력을 스키마로 검증하나.
- [ ] 클라이언트 컴포넌트로 넘기는 props에 민감한 필드가 없나.
- [ ] `NEXT_PUBLIC_*`/`EXPO_PUBLIC_*`에 비밀이 없나. 서버 전용 모듈에 `server-only`.
- [ ] `dangerouslySetInnerHTML`, 사용자 입력 URL의 `href`, 리다이렉트 대상 검사.
- [ ] 토큰 보관 위치(웹 HttpOnly 쿠키, 앱 SecureStore).

## 3. 구조·경계
- [ ] `'use client'`가 필요한 가장 작은 컴포넌트에만 있나. 큰 라이브러리를 클라이언트로 끌고 오지 않나.
- [ ] 상태가 맞는 곳에 있나(서버 데이터를 전역 스토어에 복사, URL이어야 할 필터를 `useState`).
- [ ] 캐시·재검증: 변경 후 화면이 갱신되나(`updateTag`/`revalidateTag`/쿼리 무효화). 캐시하면 안 되는 사용자별 데이터를 공유 캐시에 넣지 않았나.
- [ ] 기존 구조·명명·컴포넌트를 따르나. shadcn/ui에 있는 것을 새로 만들지 않았나.
- [ ] 요구보다 복잡하지 않나(쓰이지 않는 추상화, 한 번 쓰는 제네릭 컴포넌트).

## 4. UI·접근성
- [ ] 375px과 데스크톱에서 깨지지 않음, 긴 텍스트·긴 단어(URL, 영문)에 넘침 처리.
- [ ] `docs/DESIGN.md` 토큰을 썼나(임의 색·간격 값 `text-[#123456]`, `mt-[13px]`가 흩어져 있지 않나).
- [ ] 버튼은 `<button>`, 링크는 `<a>`/`<Link>`, 입력에 라벨, 아이콘 버튼에 이름, 포커스 표시.
- [ ] 키보드로 조작 가능, 모달 Esc·포커스 복귀.
- [ ] 이미지에 크기·`alt`.

## 5. 성능 (출시)
- [ ] 이미지: `next/image`/`expo-image`, LCP 이미지 우선 로드, `sizes`.
- [ ] 순차 await 워터폴이 없나(독립 요청은 병렬).
- [ ] 새 의존성의 크기와 필요성. 같은 일을 하는 라이브러리가 이미 있지 않나.
- [ ] 긴 목록 가상화, 입력마다 무거운 계산 없음.

## 6. 테스트·운영 (출시)
- [ ] 바뀐 동작에 맞는 테스트가 있고, 구현이 틀리면 실패하는 테스트인가.
- [ ] 버그 수정이면 재현 테스트가 있나.
- [ ] 타입 체크·린트·테스트·빌드가 CI에서 통과.
- [ ] 에러가 로깅·모니터링으로 보이나(조용히 삼키는 `catch {}` 없음).
- [ ] 앱: 네이티브 변경이 있으면 OTA가 아니라 새 빌드 필요 — 배포 계획에 반영됐나.
