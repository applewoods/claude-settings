# 프론트엔드 매뉴얼

> **팀으로 진행:** 여러 단계이거나 검증이 중요한 일은 `team-orchestration` 스킬의 "개발" 팀 구성(scout·builder·expert·verifier)으로 나눠 맡긴다. 각 팀원은 이 매뉴얼을 따른다.

## 기본 스택
- **웹**: Next.js (App Router). 템플릿 기본 설정(TypeScript)을 따른다.
- **모바일 앱**: React Native + Expo. 웹과 공유할 수 있는 로직·타입은 함께 쓴다.
- **스타일·UI**: Tailwind CSS + shadcn/ui. 모바일 앱은 NativeWind 등 Tailwind 방식에 맞는 도구를 쓴다.
- 다른 도구가 꼭 필요하면 이유를 한 줄로 설명하고 묻는다.
- **버전 확인이 먼저다.** Next.js·Expo·Tailwind는 큰 버전마다 기본 동작이 바뀐다(예: Next.js 16의 Cache Components, `middleware`→`proxy` 이름 변경). 작업 전 `package.json`의 버전을 보고, 기억과 다르면 공식 문서(nextjs.org/docs, docs.expo.dev)를 확인한다.

## 디자인
- 색·글꼴·간격은 `docs/DESIGN.md`를 따른다. 없거나 디자인을 새로 잡는 일이면 `ux-ui-design` 스킬부터 따른다.
- 랜딩·소개 페이지는 `design-taste-frontend`, 앱 화면은 이 매뉴얼과 shadcn/ui로 만든다.

## 작업 범위부터 정한다: 데모 vs 출시
| | 연구 데모·프로토타입 | 출시 서비스 |
|---|---|---|
| 목표 | 빨리 보여 주고 바꾸기 쉽게 | 오래 고치기 쉽고, 느리거나 깨지지 않게 |
| 테스트 | 핵심 흐름 수동 확인 + 타입 체크 | 단위·컴포넌트 + 핵심 흐름 E2E(`testing.md`) |
| 성능 | 눈에 띄게 느리지 않으면 통과 | Core Web Vitals 예산 지킴(`performance.md`) |
| 보안 | 비밀값을 클라이언트에 두지 않기, 서버에서 권한 확인 | + CSP·헤더·의존성 점검(`security.md`) |
| 접근성 | 키보드·라벨·대비 기본 | WCAG 2.2 AA 목표(`accessibility.md`) |

모르면 묻지 말고 `CLAUDE.md`·`docs/`에서 찾는다. 그래도 없으면 데모로 보고 시작하되, 보고에 "출시 전 할 일"을 적는다.

## 핵심 원칙
1. **서버가 기본, 클라이언트는 필요한 곳만.** 상태·이벤트·브라우저 API가 필요한 가장 작은 잎(leaf) 컴포넌트에만 `'use client'`를 붙인다. 페이지 전체를 클라이언트로 만들지 않는다.
2. **상태는 종류별로 둔다.** 서버 데이터는 서버 컴포넌트나 쿼리 캐시(TanStack Query), URL로 표현할 수 있는 것(필터·탭·페이지)은 URL, 폼 값은 폼 라이브러리, 나머지 UI 상태는 `useState`. 전역 스토어는 마지막 수단이다.
3. **파생 값은 저장하지 않는다.** 계산할 수 있는 값을 `useState`+`useEffect`로 동기화하는 것은 버그의 흔한 원인이다. 렌더 중에 계산한다.
4. **`useEffect`는 외부 시스템과 동기화할 때만.** 데이터 패칭·이벤트 처리·파생 값 계산에 쓰지 않는다.
5. **모든 비동기 UI는 4가지 상태를 가진다:** 로딩·빈 상태·에러·성공. 그리고 중복 제출 방지.
6. **서버 입력 검증과 권한 확인은 항상 서버에서.** 클라이언트 검증은 사용자 편의일 뿐이다. Server Action도 공개 엔드포인트처럼 다룬다.
7. **모바일 우선.** 375px 폭부터 만들고 넓힌다. 터치 대상 최소 44×44pt(iOS)/48dp(Android), 본문 16px 이상.
8. **shadcn/ui·검증된 라이브러리를 먼저 쓴다.** 모달·드롭다운·콤보박스를 직접 만들면 포커스·키보드·접근성이 거의 항상 빠진다.
9. 기획 문서(`docs/`)와 목업이 있으면 그 화면 구성과 흐름을 따른다. 다르게 하고 싶으면 먼저 묻는다.

## 결정 기준표
| 상황 | 선택 | 피할 것 |
|---|---|---|
| 페이지 데이터 읽기(웹) | 서버 컴포넌트에서 직접 읽기 + `<Suspense>` | 클라이언트 `useEffect`+`fetch` |
| 클라이언트에서 자주 바뀌는 서버 데이터(무한 스크롤·폴링·앱) | TanStack Query | 직접 만든 캐시·전역 스토어에 서버 데이터 복사 |
| 데이터 변경(웹, 같은 앱 안) | Server Action + 캐시 무효화 | 내부 호출만 하는 Route Handler |
| 외부·모바일 앱이 부르는 API | Route Handler(또는 별도 백엔드, `backend` 스킬) | Server Action을 외부 API로 쓰기 |
| 필터·정렬·탭·페이지 번호 | URL `searchParams` | `useState`(새로고침·공유 시 사라짐) |
| 여러 화면이 공유하는 클라이언트 상태 | Context(드물게 바뀜) → Zustand(자주 바뀜) | Redux를 처음부터 |
| 폼 | 단순: `<form action>` + `useActionState` / 복잡: React Hook Form + Zod | 입력마다 `useState` 여러 개 |
| 목록 수백 개 이상 | 페이지네이션 → 가상화(웹 TanStack Virtual, 앱 FlashList) | 전부 렌더 |
| 이미지 | `next/image`(웹), `expo-image`(앱) | 크기 없는 `<img>` |

## 작업 절차
1. **파악**: `package.json` 버전, 기존 폴더 구조·컴포넌트·스타일 규칙, `docs/DESIGN.md`·기획 문서를 본다. 기존 방식이 있으면 그것을 따른다(일관성 > 내 취향).
2. **범위 결정**: 데모인지 출시인지, 바꿀 화면과 상태(로딩·빈·에러)를 정한다.
3. **구현**: 데이터 흐름(어디서 읽고 어디서 바꾸는지)부터 정하고 UI를 붙인다. 모바일 폭부터.
4. **정적 검사**: 타입 체크(`tsc --noEmit` 또는 프로젝트 스크립트), 린트, 있으면 테스트.
5. **직접 확인**: 아래대로 실제 화면을 띄운다.
6. **보고**: 확인한 것, 확인 못 한 것, 출시 전 할 일.

## 직접 확인하고 끝낸다
- **완료라고 하기 전에 실제 화면을 띄워서 확인한다.**
  - 웹: 개발 서버를 띄우고 내장 브라우저로 열어, 모바일 폭(375px)과 데스크톱 폭에서 확인한다. 콘솔 에러·하이드레이션 경고도 확인한다.
  - 앱: Expo로 iOS 시뮬레이터(또는 Expo 웹)에서 띄워 확인한다.
- 상태를 일부러 만들어 본다: 빈 데이터, 느린 응답(네트워크 스로틀), 실패 응답, 긴 텍스트.
- 키보드만으로 바꾼 화면의 주요 동작을 해 본다(Tab·Enter·Esc).
- 확인한 화면과 확인하지 못한 부분을 보고한다.

## 완료 기준
- [ ] 바꾼 화면을 브라우저(또는 시뮬레이터)에서 직접 열어 봤다.
- [ ] 모바일 폭과 데스크톱 폭 모두에서 레이아웃이 깨지지 않는다(가로 스크롤 없음).
- [ ] 콘솔에 새 에러·하이드레이션 경고가 없다.
- [ ] 로딩·빈 상태·에러 상태가 처리돼 있고, 제출 버튼은 중복 클릭이 막힌다.
- [ ] 타입 체크·린트가 통과한다(있으면 테스트도).
- [ ] 키보드로 조작할 수 있고, 입력에 라벨이, 아이콘 버튼에 이름이 있다.
- [ ] 비밀값이 클라이언트 번들(`NEXT_PUBLIC_*`, `EXPO_PUBLIC_*`)에 없다.
- [ ] 출시 서비스면 `review-checklist.md`의 출시 항목을 확인했다.
- [ ] 배포 전이면 `web-design-guidelines`로 바꾼 화면 코드를 검사했다.
