# 논문 리뷰 매뉴얼

목적은 **내 연구에 쓸 수 있는 정확한 기록**을 남기는 것이다. 좋은 리뷰는 요약보다 판단이 많다: 무엇을 주장했고, 그 주장을 실험이 실제로 뒷받침하는지, 내 연구에 무엇을 가져올 수 있는지.

> **팀으로 진행:** 정독이나 여러 편을 한 번에 할 때는 `team-orchestration` 스킬대로 나눈다. builder(sonnet)가 추출, expert(opus)가 비판적 평가·내 연구 연결, verifier가 수치 대조. 훑기 한 편은 직접 한다.

## 0. 준비
1. `~/wiki/CLAUDE.md`(위키 규칙), `~/wiki/index.md`, `~/wiki/wiki/my-research.md`(내 연구)를 읽는다. 같은 논문 페이지가 이미 있으면 새로 만들지 않고 갱신한다.
2. PDF를 `~/wiki/raw/<저자성><연도>-<핵심어>.pdf`로 복사한다(원본은 그대로 둔다). arXiv 링크면 내려받기 전에 파일명·출처·크기를 알리고 확인을 받는다. Zotero에서 찾을 때는 `~/Zotero/storage/*/`를 검색한다.
3. PDF는 Read 도구로 페이지 단위로 읽는다(한 번에 20쪽까지). 부록은 본문 판단에 필요할 때만 읽는다.

## 1. 깊이
사용자가 따로 말하지 않으면 **정독**이다.
| 깊이 | 하는 일 | 결과 |
|---|---|---|
| 훑기 | 제목·초록·그림·결론만. 읽을 가치 판단 | 3~5줄 + "정독 권함/불필요" |
| 표준 | 2~4절 (추출 + 주장-근거 + 내 연구) | 논문 페이지 |
| 정독 | 2~6절 전부 + 수치 대조 | 논문 페이지 + 개념 페이지 갱신 |

## 2. 유형 판정과 추출
- 논문 유형을 정하고 해당 체크리스트를 읽는다. 여러 유형이 섞이면 둘 다 읽는다.
  - 모델·기법 제안 + 벤치마크 → `references/checklist-ml.md`
  - 특정 분야(의료·산업·교육 등)에 AI 적용 → `references/checklist-applied.md`
  - 사용자 실험·인터뷰·설문 → `references/checklist-hci.md`
- 추출할 것: 연구 문제, **기여 주장 목록(C1, C2…, 저자 표현에 가깝게)**, 방법 핵심, 데이터, 베이스라인, 지표, 주요 결과, 저자가 밝힌 한계.
- **모든 수치는 원문 위치와 함께 적는다:** `28.4 BLEU (Table 2, p.8)`. 위치를 못 찾은 수치는 적지 않거나 `[확인 필요]`로 둔다. 리뷰에서 가장 비싼 실수가 틀린 수치이고, 위치가 있어야 나중에 검증할 수 있기 때문이다.

## 3. 주장-근거 대응
기여 주장마다 근거를 표로 짝짓는다. 이 표가 리뷰의 중심이다. 초록의 주장과 실험이 실제로 보여 준 것의 차이가 여기서 드러난다.

| 주장 | 근거 (실험·표·그림) | 판정 | 이유 |
|---|---|---|---|
| C1: … | Table 2 | 충분 / 부분 / 부족 / 근거 없음 | 한두 줄 |

판정 기준: **충분** = 주장 범위 그대로 직접 보여 줌. **부분** = 일부 조건·데이터셋에서만, 또는 대안 설명을 배제 못 함. **부족** = 실험이 주장과 다른 것을 측정. **근거 없음** = 대응하는 실험이 없음.

## 4. 실험 설계 평가
체크리스트 항목 중 이 논문에 해당하는 것만 쓴다. 해당 없는 항목을 나열하지 않는다. 각 지적에는 "그래서 결론이 어떻게 약해지는지"를 한 줄 붙인다. 영향 없는 흠은 쓰지 않는다.
- 저자 주장과 내 평가를 섞지 않는다. 한계 절에서는 `저자:`와 `평가:`로 나눠 적는다.
- 지금 기준으로 보면 낡은 부분(오래된 논문)은 비판이 아니라 "당시 맥락"으로 구분해 적는다.

## 5. 내 연구와의 관계
`my-research.md`의 연구 질문·진행 중 프로젝트에 비춰 쓴다.
- **가져올 것:** 방법·설계·평가 방식·데이터셋 중 구체적으로 무엇을, 어디에.
- **겹치는 정도:** 내 연구와 같은 문제를 푸는지, 내 기여를 위협하는지.
- **남은 gap:** 이 논문이 안 한 것 중 내 연구가 할 수 있는 것. `research-design`의 선행연구 지도에 쓸 수 있게 한 줄로.
- `my-research.md`가 없거나 비어 있으면 지어내지 말고, 이 절에 "my-research.md 비어 있음 — 일반적 활용 가능성만 적음"이라고 쓰고 사용자에게 채우자고 제안한다.

## 6. 위키 반영과 검증
1. `templates/paper-page.md` 양식으로 `~/wiki/wiki/papers/<파일명>.md`를 쓴다.
2. 논문의 핵심 개념·기법·데이터셋 페이지를 만들거나 갱신한다. 정독이면 보통 3~6개다. 새 내용에는 이 논문 링크를 출처로 단다.
3. 정독이면 **수치 대조**를 한다: 페이지에 적은 수치를 하나씩 원문 위치에서 다시 확인하고, 틀린 것은 고친다. 그다음 verifier에게 같은 대조를 맡긴다. 공개 논문은 그대로 보내도 되고, 미공개 원고(심사 중·공동연구 초안)는 외부로 보내기 전에 사용자에게 묻는다.
4. 이후는 `wiki` 스킬의 공통 절차(index 갱신 → lint → log → 커밋)를 따른다.
5. 사용자에게는 채팅으로 핵심 3~5줄과 주장-근거 판정 요약, 내 연구에 가져올 것을 보여 주고 페이지 경로를 알린다.

## 완료 기준
- [ ] 기여 주장 전부가 주장-근거 표에 있고, 판정마다 이유가 있다.
- [ ] 모든 수치에 원문 위치가 있다(또는 `[확인 필요]`). 정독이면 수치 대조를 마쳤다.
- [ ] 저자 주장과 내 평가가 구분돼 있다.
- [ ] 내 연구 절이 `my-research.md`에 근거하거나, 비어 있다고 명시했다.
- [ ] 위키 lint를 통과했고 커밋했다.
