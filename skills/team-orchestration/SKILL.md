# 팀 운영 매뉴얼

메인 Claude가 **오케스트레이터**다. 일을 나누고, 맞는 팀원과 모델에 맡기고, 결과를 검증해 합친다.
팀원 **역할**은 4종류이고(인원 수가 아니다), 업무 지식은 스킬(매뉴얼)에 있다. 업무마다 새 에이전트를 만들지 않는다.

## 1. 팀을 꾸릴지 먼저 판단한다
| 일의 크기 | 진행 |
|---|---|
| 질문 하나, 파일 한두 개 수정, 몇 번의 명령으로 끝나는 일 | 오케스트레이터가 **직접** 한다. 팀을 부르면 느리고 비싸기만 하다. |
| 조사할 곳이 많거나, 서로 독립된 작업이 2개 이상이거나, 결과 검증이 중요한 일 | **팀으로** 진행한다. |
| 애매하면 | 팀으로 하되 인원을 최소로(조사 1 + 검증 1). |

## 2. 팀원과 모델
| 팀원 | 기본 모델 | 맡기는 일 |
|---|---|---|
| `scout` | haiku | 찾기·읽기·요약, 자료 조사 (읽기 전용) |
| `builder` | sonnet | 보통 난이도 구현·분석·초안 |
| `expert` | opus | 설계 결정, 연구 설계, 논문 핵심, 복잡한 디버깅 |
| `verifier` | **Codex CLI** (OpenAI) | 완료 기준으로 독립 검증 (고치지 않음). `codex-verify.sh`를 오케스트레이터가 직접 실행하거나, 병렬일 때 haiku 래퍼(`verifier`)가 실행 |

**모델 조정 규칙** (Agent 도구의 `model`로 덮어쓴다)
- 한 단계 올린다: 틀리면 비용이 큰 일(논문 본문, 제출물, 운영 DB·배포, 보안·개인정보), 앞선 시도가 실패한 일, 판단 근거가 여러 자료에 흩어진 일.
  - verifier는 Claude 모델이 아니라 Codex가 판정한다. 중요한 검증에서 Codex 모델을 바꾸려면 브리핑에 `-m <모델>`을 적는다.
- 한 단계 내린다: 양은 많지만 판단이 거의 없는 일(형식 변환, 목록 정리, 단순 반복 수정) → builder를 haiku로.
- 오케스트레이터 자신(메인 세션)의 모델이 일에 비해 과하거나 부족하면, 바꾸자고 한 줄로 제안한다. 허락 없이 바꾸지 않는다.

### 인원 정하기
- 4종류는 역할이고, 인원은 일에 맞게 정한다. 같은 역할을 여러 명 동시에 부를 수 있고, 필요 없는 역할은 부르지 않는다.
  - 늘리는 예: 선행연구를 주제 3개로 나눠 scout 3명 병렬 / 서로 다른 화면·모듈을 builder 2~3명이 파일 단위로 나눠 구현
  - 줄이는 예: 조사만 필요하면 scout 1명 / 이미 정해진 설계를 구현만 하면 builder 1명 + 검증
- 한 번에 동시에 돌리는 팀원은 보통 5명 이내로 한다. 그보다 많아지면 단계를 나눠서 진행한다(합치고 검증하는 비용이 커진다).
- 같은 파일을 두 명이 동시에 고치지 않는다. 나눌 수 없으면 한 명에게 맡긴다.
- 4가지 역할로 해결되지 않는 일이 **반복해서** 생기면(예: 특정 도구 전담), 새 역할을 만들자고 나에게 제안한다. 임의로 만들지 않는다.

## 3. 업무별 기본 팀 구성
디자인·개발·논문·데이터 분석 등 모든 업무에 적용한다. 아래는 출발점이고, 일에 맞게 역할을 빼거나 같은 역할을 여러 명으로 늘린다. 각 팀원은 해당 업무 스킬(괄호)을 따른다.

| 업무 (스킬) | scout · haiku | builder · sonnet | expert · opus | verifier · Codex |
|---|---|---|---|---|
| **논문 작성** (`paper-writing`) | 선행연구·문헌 찾기, 논문 요약 | 방법·결과 등 정해진 내용의 초안, 표·그림 설명 | 논지·구조, 서론·기여·논의 등 핵심 문단, 리뷰어 답변 전략 | 인용 실존·서지 확인, 수치가 결과와 일치하는지, 원문 보존 |
| **데이터 분석** (`data-analysis`) | 데이터 구조·결측 파악, 관련 기법·선행 사례 조사 | 전처리·학습·평가 스크립트, 표·그림 생성 | 실험·분석 설계, 통계 방법 선택, 결과 해석 | 코드 실제 실행·재현, 데이터 누수 점검, 보고 수치 대조 |
| **서비스 기획** (`service-planning`, `synthetic-user-research`) | 유사·경쟁 서비스 조사, 페르소나 분포 근거(통계·기존 데이터) 찾기 | PRD·유저 스토리·화면 흐름·HTML 목업 초안 | MVP 범위·우선순위, 개인정보·보안 판단 | 기획 문서 완료 기준, 빠진 시나리오 점검 |
| **UX/UI 디자인** (`ux-ui-design`) | 참고 디자인·DESIGN.md 후보 조사 | 화면 제작(랜딩은 `design-taste-frontend`, 앱은 `frontend`) | 디자인 방향·디자인 시스템 결정 | `web-design-guidelines` 검사, 브라우저 확인 결과·디자인 검토 |
| **개발** (`frontend` · `backend` · `database`) | 코드베이스 위치·영향 범위 파악, 라이브러리 문서 조사 | 기능 구현, 테스트 작성 (파일 단위로 나눠 병렬) | 아키텍처·스키마·인증 설계, 원인 불명 버그 | 테스트·빌드 실행, 입력 검증·권한·비밀값 점검 |
| **문서·기획서** | 자료 수집·요약 | 초안 작성 | 구성·핵심 메시지 | 요청 사항 대조, 근거 없는 주장 표시 |

## 4. 진행 순서
1. **분해**: 일을 결과물 단위로 나누고, 각 조각의 완료 기준을 적는다. 관련 스킬이 있으면 그 완료 기준을 쓴다.
2. **배정**: 조각마다 팀원과 모델을 고른다. 서로 의존하지 않는 조각은 한 번에 병렬로 보낸다. 같은 파일을 두 팀원이 동시에 고치게 하지 않는다.
3. **지시(브리핑)**: 팀원은 지금까지의 대화를 모른다. 아래 양식으로 필요한 것을 모두 적어 보낸다.
4. **합치기**: 결과를 받아 서로 맞는지 확인하고 하나로 합친다. 팀원의 보고는 주장일 뿐이니, 중요한 부분은 직접 확인한다.
5. **검증**: 아래 "7. 독립 검증"대로 한다. 실패 항목은 해당 팀원(또는 직접)이 고치고 다시 검증한다. 최대 2회.
6. **보고**: 나에게 결론, 누가 무엇을 했는지(팀원·모델), 검증 결과(Codex 지적의 수용·기각 포함), 확인 못 한 것을 짧게 보고한다.

## 5. 브리핑 양식
```
목표: (이 조각이 무엇을 위해 필요한지 한 줄)
할 일: (구체적인 범위. 건드려도 되는 파일·폴더)
참고: (관련 파일 경로, 따를 스킬 이름, 이미 정해진 결정)
하지 말 것: (범위 밖 파일, 삭제·설치·커밋·푸시 등)
완료 기준: (체크할 항목)
보고 형식: (팀원 정의의 형식 + 추가로 필요한 것)
```

## 6. 지켜야 할 것
- 파일 삭제·덮어쓰기, 설치, 커밋·푸시, 외부로 보내는 일은 팀원에게 맡기지 않는다. 오케스트레이터가 나에게 확인받고 직접 한다.
- 팀원이 막히거나 범위가 바뀌면 추측으로 밀어붙이지 말고 오케스트레이터가 다시 판단한다.
- 같은 종류의 팀 작업이 반복되면, 그 업무의 스킬(매뉴얼)을 만들거나 고치자고 제안한다.

## 7. 독립 검증
**원칙: 근거 기반·비판적 검증.** 검증자는 "틀렸다"는 가정에서 출발해 반증을 시도하고, 직접 확인한 근거로만 통과시킨다. 모든 판정에 근거 유형([직접 확인]/[간접 추론]/[확인 불가])을 붙이고, 완료 기준 밖의 문제도 심각도(치명/중요/사소)와 함께 찾는다. 원칙 전문과 업무별 비판 질문은 `~/claude-settings/verification/`에 있다.

### 검증 강도
| 단계 | 언제 | 방법 |
|---|---|---|
| 기본 | 작은 일(팀 없이 직접 한 일) | 오케스트레이터가 위 원칙과 스킬 완료 기준으로 스스로 확인. 근거를 보고에 적는다. |
| 독립 | 팀으로 한 일, 결과물이 있는 일 | Codex 검증 (`-e high`) |
| 강화 | 논문 제출, 운영 배포·DB 변경 등 되돌리기 어려운 일 | Codex 검증 (`-e xhigh`) + 최종 판단은 나에게 받는다 |

### 실행
```bash
~/claude-settings/scripts/codex-verify.sh "<검사할 폴더>" <브리핑 파일 | -> -t <유형> [--run] [--web] [-e low|medium|high|xhigh] [-m 모델] [--label 이름] [--no-save]
```
- Bash timeout 600000. 출력 첫 줄이 `[Codex 독립 검증 결과]`인지 확인한다. 다른 작업과 병렬로 돌릴 때만 `verifier` 에이전트에 맡기고, 그 보고에 이 표시가 없으면 검증된 것으로 보지 않는다.
- `-t`: `paper`(논문) · `data`(분석·실험) · `dev`(개발) · `design`(디자인·화면) · `plan`(기획·문서). 여러 개는 쉼표로.
- `--run`: 테스트·분석 코드를 실제로 돌려야 할 때. 원본의 임시 복사본에서 실행하고 끝나면 지운다. **데이터 분석·개발 검증은 기본으로 붙인다.**
- `--web`: 인용 실존·출처 확인이 필요할 때. **논문 검증은 기본으로 붙인다.**
- 브리핑에는 검증 대상, 완료 기준(스킬의 완료 기준 포함), 참고 파일을 적는다. 만든 쪽의 자기 평가는 넣지 않는다.
- 결과는 `<검사할 폴더>/docs/verification/날짜_이름.md`에 저장된다(`--no-save`로 끔).

### Codex와 판단이 다를 때
- Codex 지적을 조용히 넘기지 않는다. 각 지적에 대해 **수용**(고친다) 또는 **기각**(근거를 댄다) 중 하나로 처리한다.
- 기각하려면 Codex 근거보다 강한 [직접 확인] 근거가 있어야 한다. 근거가 맞서면 `expert`(opus)에게 양쪽 근거를 주고 세 번째 의견을 받거나, 나에게 결정을 묻는다.
- 처리 결과를 검증 기록 파일의 "오케스트레이터 처리 기록"에 적는다.

### 막혔을 때
- Codex가 없거나 실패하면 Claude로 대신 검증하지 않는다. 나에게 알리고 어떻게 할지 묻는다.
- Codex가 [확인 불가]로 남긴 항목은 오케스트레이터가 직접 확인하고, 보고에 누가 확인했는지 적는다.

### 데이터 반출
- Codex로 검증하면 대상 파일 내용이 OpenAI로 전송된다. 프로젝트 `CLAUDE.md`의 "Codex 검증" 설정을 따른다(허용 / 금지 / 매번 확인). 설정이 없으면 미공개 데이터·개인정보·민감한 원고가 있는지 보고 나에게 확인받는다.

## 완료 기준
- [ ] 팀 구성 여부를 일의 크기로 판단했다(작은 일은 직접).
- [ ] 조각마다 완료 기준과 팀원·모델 배정 이유가 있고, 인원은 일에 맞게 정했다.
- [ ] 결과물이 있는 일은 강도에 맞게 Codex 독립 검증을 거쳤고, 모든 지적을 수용 또는 근거 있는 기각으로 처리했다.
- [ ] 최종 보고에 팀원·모델별 역할과 확인 못 한 것이 들어 있다.
