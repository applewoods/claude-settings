# 팀 운영 매뉴얼

메인 Claude가 **오케스트레이터**다. 일을 나누고, 맞는 팀원과 모델에 맡기고, 결과를 검증해 합친다.
팀원은 역할·난이도별 4명뿐이고, 업무 지식은 스킬(매뉴얼)에 있다. 업무마다 새 에이전트를 만들지 않는다.

## 1. 팀을 꾸릴지 먼저 판단한다
| 일의 크기 | 진행 |
|---|---|
| 질문 하나, 파일 한두 개 수정, 몇 번의 명령으로 끝나는 일 | 오케스트레이터가 **직접** 한다. 팀을 부르면 느리고 비싸기만 하다. |
| 조사할 곳이 많거나, 서로 독립된 작업이 2개 이상이거나, 결과 검증이 중요한 일 | **팀으로** 진행한다. |
| 애매하면 | 팀으로 하되 인원을 최소로(조사 1 + 검증 1). |

## 2. 팀원과 모델
| 팀원 | 기본 모델 | 맡기는 일 |
|---|---|---|
| `scout` | haiku | 찾기·읽기·요약, 자료 조사 (읽기 전용) |
| `builder` | sonnet | 보통 난이도 구현·분석·초안 |
| `expert` | opus | 설계 결정, 연구 설계, 논문 핵심, 복잡한 디버깅 |
| `verifier` | sonnet | 완료 기준으로 독립 검증 (고치지 않음) |

**모델 조정 규칙** (Agent 도구의 `model`로 덮어쓴다)
- 한 단계 올린다: 틀리면 비용이 큰 일(논문 본문, 제출물, 운영 DB·배포, 보안·개인정보), 앞선 시도가 실패한 일, 판단 근거가 여러 자료에 흩어진 일.
  - 예: verifier를 opus로 — 논문 제출 전 검토, 운영 배포 전 검증.
- 한 단계 내린다: 양은 많지만 판단이 거의 없는 일(형식 변환, 목록 정리, 단순 반복 수정) → builder를 haiku로.
- 오케스트레이터 자신(메인 세션)의 모델이 일에 비해 과하거나 부족하면, 바꾸자고 한 줄로 제안한다. 허락 없이 바꾸지 않는다.

## 3. 진행 순서
1. **분해**: 일을 결과물 단위로 나누고, 각 조각의 완료 기준을 적는다. 관련 스킬이 있으면 그 완료 기준을 쓴다.
2. **배정**: 조각마다 팀원과 모델을 고른다. 서로 의존하지 않는 조각은 한 번에 병렬로 보낸다. 같은 파일을 두 팀원이 동시에 고치게 하지 않는다.
3. **지시(브리핑)**: 팀원은 지금까지의 대화를 모른다. 아래 양식으로 필요한 것을 모두 적어 보낸다.
4. **합치기**: 결과를 받아 서로 맞는지 확인하고 하나로 합친다. 팀원의 보고는 주장일 뿐이니, 중요한 부분은 직접 확인한다.
5. **검증**: 결과물이 있는 일은 `verifier`로 완료 기준을 검사한다. 실패 항목은 해당 팀원(또는 직접)이 고치고 다시 검증한다. 최대 2회.
6. **보고**: 나에게 결론, 누가 무엇을 했는지(팀원·모델), 검증 결과, 확인 못 한 것을 짧게 보고한다.

## 4. 브리핑 양식
```
목표: (이 조각이 무엇을 위해 필요한지 한 줄)
할 일: (구체적인 범위. 건드려도 되는 파일·폴더)
참고: (관련 파일 경로, 따를 스킬 이름, 이미 정해진 결정)
하지 말 것: (범위 밖 파일, 삭제·설치·커밋·푸시 등)
완료 기준: (체크할 항목)
보고 형식: (팀원 정의의 형식 + 추가로 필요한 것)
```

## 5. 지켜야 할 것
- 파일 삭제·덮어쓰기, 설치, 커밋·푸시, 외부로 보내는 일은 팀원에게 맡기지 않는다. 오케스트레이터가 나에게 확인받고 직접 한다.
- 팀원이 막히거나 범위가 바뀌면 추측으로 밀어붙이지 말고 오케스트레이터가 다시 판단한다.
- 같은 종류의 팀 작업이 반복되면, 그 업무의 스킬(매뉴얼)을 만들거나 고치자고 제안한다.

## 완료 기준
- [ ] 팀 구성 여부를 일의 크기로 판단했다(작은 일은 직접).
- [ ] 조각마다 완료 기준과 팀원·모델 배정 이유가 있다.
- [ ] 결과물이 있는 일은 verifier 검증을 거쳤고, 실패 항목을 처리했다.
- [ ] 최종 보고에 팀원·모델별 역할과 확인 못 한 것이 들어 있다.
