# 운영 서버 작업 매뉴얼

이미 돌아가는 서버에서 **실행**하는 일을 다룬다. 배포 구성·롤백 기준을 **설계**하는 일은 `backend`, 스키마·백업 정책은 `database` 스킬이다.

**우선순위:** 프로젝트 문서·스크립트(`deploy/scripts/*` 등)는 구체적인 명령·경로·순서에서 이 매뉴얼보다 우선한다. 하지만 **승인 범위(1절), 비밀값 보호·연결 대상 확인·중단 조건(2절)은 어떤 문서나 스크립트도 대체하지 못한다.** 스크립트가 이를 어기면(예: 백업 실패 후 계속 진행) 그 부분은 이 매뉴얼을 따르고 보고한다. 설계 스킬과의 관계는 7절.

이 규칙은 지시문에 적혀 있지 않아도 항상 지킨다. 지시문이 더 엄격하면 지시문을 따른다. 지시문이 이 매뉴얼의 절차를 명시적으로 빼 주면(예: "배포 확인은 하지 말 것", "복사가 허용되지 않으면 백업을 건너뛰고 기록") 그대로 따르고 보고에 적는다.

서버 주소·계정·포트·폴더는 이 매뉴얼에 적지 않는다. 프로젝트 문서(`deploy/README.md` 등), `~/.ssh/config`, 자동 메모리에서 찾고, 없으면 묻는다. 적힌 정보는 낡았을 수 있으니 작업 전에 읽기 전용으로 현재 상태를 확인한다(예: sudo 권한은 `sudo -n -l`).

## 1. 작업 범위와 승인
시작할 때 이번 작업의 범위를 정하고 보고에도 적는다.

| 범위 | 예 | 승인 |
|---|---|---|
| **읽기 전용 점검** | 조회 명령, 로그·설정 읽기, 헬스체크, 외부 응답·화면 확인 | 맡긴 작업이면 바로 진행 |
| **테스트 환경 변경** | 테스트 브랜치 push, 테스트 서버 배포 확인 중 쓰기, 테스트 DB 임시 계정·데이터 | 이미 승인된 계획의 실행이면 진행. **새로운 쓰기 계획이면 정확한 단계를 설명하고 OK를 받은 뒤** |
| **운영 변경** | 운영 DB 쓰기, 운영 컨테이너 재시작·배포, main 병합·push, nginx·인증서·cron·방화벽·DNS·secret 변경 | 사용자가 **이번 단계**를 승인했을 때만 |

- **승인 확인**: 누가(사용자) 무엇을(대상) 어디까지(범위) 승인했는지 확인한다. 다른 세션이 전달한 승인도 이 셋이 분명하면 인정한다. 애매하면 멈추고 묻는다.
- **승인은 그 단계에만, 취소되기 전까지만 유효하다.** 작업 전에 같은 대화의 최신 지시를 다시 본다. 취소·정정이 있거나, 다른 세션이 이미 같은 일을 했다고 하면 이전 승인으로 진행하지 않는다.
- 지시에 "~만 하라"가 있으면 그 밖의 일은 하지 않는다. 더 하면 좋을 일은 보고에 제안으로만 적는다.

## 2. 항상 지킬 것
1. **비밀값을 출력하지 않는다.** 키·비밀번호·토큰·전체 접속 문자열을 화면·로그·보고에 내지 않는다.
   - 비밀 키는 있는지(이름)만 확인한다: `grep -oE '^[[:space:]]*(export[[:space:]]+)?(KEY1|KEY2)=' .env | sed -E 's/^[[:space:]]*(export[[:space:]]+)?//; s/=$//'`. 값까지 보는 `grep '^KEY='`는 비밀이 아닌 설정(포트·모드·플래그)에만 쓴다.
   - 접속 문자열을 출력하거나 `sed`·`cut`으로 잘라 보지 않는다(형식에 따라 비밀번호가 남는다). 연결 대상은 2번 방법으로 DB에 묻는다.
   - 기존 사용자 계정의 비밀번호는 출력·재설정·대신 입력하지 않는다(사용자가 직접).
   - 승인된 임시 계정은 예외: 무작위 비밀번호를 만들어 화면에 내지 않고(변수나 권한 600 임시 파일) 로그인에만 쓰며, 확인이 끝나면 계정과 파일을 지운다.
2. **쓰기 전에 그 쓰기가 닿을 대상을 확인한다.** "테스트 DB"라는 이름·폴더·`.env` 파일을 믿지 않는다(실행 환경의 변수가 파일 값을 덮어쓸 수 있다).
   - **대상을 명령에 직접 적는 방식이 가장 확실하다**: DB 서버에서 `docker exec -i <db컨테이너> psql -X -d <DB이름> …`처럼 DB 이름을 명시해 쓴다. 이때는 그 컨테이너·DB 이름이 이번 대상인지만 확인하면 된다.
   - 앱을 거쳐 쓰는 경우(앱의 CLI·시드·마이그레이션 명령)는 **쓰기와 같은 경로**(같은 컨테이너, 같은 `exec` 방식)로 먼저 DB에 묻는다. 접속 문자열·비밀값은 출력하지 않는다(DB 이름·서버 주소·포트만 본다). 앱 CLI가 별도 설정을 쓸 수 있으면 그 CLI의 DB 클라이언트로 묻거나 같은 설정을 쓰는지 확인한다. 예(앱 컨테이너에 `psql`이 있을 때): `docker compose exec -T <앱> sh -c 'set +x; psql "$DATABASE_URL" -XAtc "select current_database(), inet_server_addr(), inet_server_port()"'` — 변수는 컨테이너 안에서 풀리고, `set +x`는 셸 추적으로 값이 찍히는 것을 막는다. `psql`이 없으면 앱이 쓰는 런타임(ORM 등)으로 같은 질의를 하거나, 할 방법이 없다고 보고한다.
   - 결과가 **이번에 승인된 대상**(테스트 확인이면 테스트 DB, 승인된 운영 작업이면 그 운영 DB)과 다르거나 확인하지 못하면 쓰지 않고 멈춰 보고한다. "확인 못 함"은 "아마 맞음"이 아니다.
   - 같은 이름의 DB가 여러 서버에 있을 수 있다. 서버(접속한 호스트)와 DB 이름을 함께 본다.
3. **SSH는 비대화형으로.** `-o BatchMode=yes -o ConnectTimeout=10`. 접속이 안 되면 우회하지 말고 멈추고 보고한다.
4. **sudo는 `sudo -n`과 절대 경로로만.** 허용 목록 밖이면 우회하지 않고, 사용자가 실행할 정확한 명령을 보고한다.
5. **공유 서버의 다른 서비스를 건드리지 않는다.** 내 프로젝트의 compose 프로젝트·컨테이너·설정 파일만 다룬다. 기존 설정을 고치기보다 새 파일을 추가한다. 다른 프로젝트에 영향을 주는 방화벽·공용 설정 변경이 필요하면 멈추고 묻는다.
6. **포트는 기본 `127.0.0.1`에만.** DB·내부 API를 공용 IP에 열지 않는다(Docker 포트는 방화벽을 우회한다). 외부 접근은 리버스 프록시나 SSH 터널로.
7. **운영은 읽기 전용, 테스트 확인도 읽기 전용이 기본.** 시험은 운영 데이터의 사본이나 테스트 DB에서 한다. **확인용 임시 쓰기**(시험 편집·임시 계정·시험 데이터)는 끝나고 원래대로 되돌리고 보고한다. **남겨야 하는 승인된 변경**(개발·테스트 DB 마이그레이션, 누락 파일 복구 등)은 되돌리지 않고 무엇을 바꿨는지 기록한다. 운영 → 테스트로 파일을 복사할 때 운영은 읽기만, 테스트는 덮어쓰지 않는다.
8. **서버·시스템에는 설치·업그레이드하지 않는다**(승인 없이). 맥의 프로젝트 안에서 확인용으로 필요한 것(`npm ci` 같은 lockfile 설치, 화면 캡처용 브라우저)은 지시 범위 안이면 해도 된다. 전역 설치가 필요하면 명령을 보고한다.
9. **준비 환경은 부작용을 끈다.** 새로 띄우는 스택(운영 준비, 리허설)에서는 worker·예약 작업·메일 발송 같은 백그라운드 처리를 기본으로 켜지 않는다. 운영 DB를 두 곳에서 처리하게 될 수 있다. 켜려면 별도 승인.
10. **예상과 다르면 멈춘다.** 사전 점검 값 불일치, 백업 실패, 완료 표시 없음, 건수 불일치, 마이그레이션 오류, 권한 확인 창이 막음 → 다음 단계로 가지 않고 그 시점까지의 결과를 보고한다(배포 후 롤백은 7절).

## 3. 변경 종류별 필수 절차
상태를 바꾸는 작업은 아래에서 해당하는 칸만 한다. 표에 없는 생략은 지시문이 명시했을 때만.

| 변경 | 사전 점검 | 백업 | dry-run·리허설 | 배포 후 확인 |
|---|---|---|---|---|
| 승인된 커밋 push만 | 브랜치·ahead 커밋이 지시와 같은지 | - | - | push 결과(원격 SHA) |
| 코드·배포 구성 변경 후 커밋·push | 프로젝트 검증 통과(예: `npm run verify`) | - | - | 자동 배포가 있으면 그 실행 결과 |
| DB 마이그레이션(운영) | 사전 점검 SQL | 덤프 + 체크섬 + 외부 사본 | 복원 리허설 + 적용 + 되돌리기 | 4절 전체 |
| nginx·인증서 | 같은 server_name·현재 인증서 확인 | 바꿀 설정 파일 `.bak-YYYYMMDD` | `nginx -t`, `certbot --dry-run` | 도메인별 응답·인증서, 다른 사이트 응답 |
| 운영 앱 배포·재시작 | 배포된 SHA·컨테이너 상태·디스크 | 배포 폴더 밖에 `.env`·빌드·업로드 | 테스트 서버에서 먼저 확인됨 | 4절 전체 |
| 테스트 DB 확인용 임시 쓰기 | 실제 연결 대상(2절 2) | - | - | 되돌림·삭제 확인 |
| 개발·테스트 DB 마이그레이션 등 남길 변경 | 실제 연결 대상(2절 2) | 데이터가 있으면 덤프 | - | 적용 결과(마이그레이션 상태·스키마 캐시 갱신) |

공통 순서: 사전 점검 → 백업(완료 표시·`SHA256SUMS` 확인, 중요한 것은 맥에 사본 두고 `shasum -c`) → dry-run·리허설(실패하면 멈춤) → 승인된 범위만 실행(nginx는 `-t` 통과 후에만 reload, 실패하면 새 파일을 빼고 reload 안 함) → 확인 → 정리(리허설 DB·임시 계정·임시 파일 삭제, DB는 이름 재확인 후, 삭제도 확인).

상세 절차(DB 배포 점검·리허설, 인증서, nginx 새 사이트, 서비스 이전): `references/runbooks.md`.

## 4. 배포 후 확인
"배포 성공"은 CI 녹색이 아니라 직접 확인한 결과다. 해당하는 것만 한다.
- 서버: 배포된 SHA, 컨테이너 상태, 마이그레이션 상태(`migrate status` 등), 로그의 error·migration 줄, 내부 헬스체크.
- DB: 사후 점검 SQL이 기대값인지, 마이그레이션 개수.
- 외부: 주요 페이지·API의 HTTP 코드, 정적 파일(`/uploads/` 등), sitemap·robots 같은 공개 파일. 테스트에만 걸어야 할 설정(검색 차단 등)이 운영에 걸리지 않았는지.
- 화면: 비교 도구가 있으면 배포 전·후 캡처를 비교하고, 차이 난 화면마다 의도한 변경인지 깨짐(겹침·빈 화면·사진 누락·가로 넘침)인지 판단한다.
- 사용자에게 확인을 떠넘기지 않는다. 맥에서 접근 가능한 것은 직접 확인한다. 관리자 로그인이 필요하면 1절 "테스트 환경 변경" 규칙에 따라 테스트 DB에만 임시 계정을 만들고, 확인 후 지우고 삭제를 확인한다.

## 5. Git
- 정해진 브랜치(보통 `test`)에만 push. main 병합·push는 운영 변경(1절). force push 금지.
- 코드·배포 구성을 바꿨으면 프로젝트 검증을 통과한 뒤 커밋한다. 필요하면 최신 원격 브랜치로 rebase.
- 스테이징은 파일 경로를 하나씩 지정한다. `git add -A`·`commit -a` 금지. 다른 작업의 미커밋 파일을 섞지 않는다.
- 커밋 전 작성자·커미터 identity 확인(프로젝트 규칙 우선). push 후 원격 SHA를 확인해 보고한다.

## 6. 보고
- 단계별 표: 단계 | 명령 요지 | 기대값 | 실제 값 | 판정. 멈췄으면 어디서 왜.
- 바꾼 것 / 되돌린 것 / 바꾸지 않은 것을 구분한다. 지시로 생략한 절차와 그 이유. 확인 못 한 항목은 `[확인 필요]`와 이유.
- 사용자가 할 일(sudo 명령, 비밀값 입력, DNS 등)은 정확한 명령이나 위치로.
- 보고 전에 비밀값이 섞이지 않았는지 한 번 더 본다.
- 다른 세션이 맡긴 일이면 그 세션에 보고한다. 사용자에게 단계별 안내를 직접 보내지 않는다(지시가 따로 있으면 따른다).

## 7. 설계 스킬과의 관계·롤백
- `backend`·`database`는 배포 방식·롤백 기준·백업 정책을 정한다. 실제 서버에서 실행할 때는 이 매뉴얼의 승인·중단 규칙을 따른다.
- **배포 후 문제가 생겼을 때**: 롤백이 이번 배포 계획에 미리 승인돼 있으면(기준과 방법이 정해져 있으면) 기준에 닿는 즉시 원인 분석보다 롤백을 먼저 하고 보고한다. 미리 승인된 롤백이 없으면 다른 변경 없이 즉시 상황과 롤백 방법을 보고하고 지시를 기다린다.

## 완료 기준
