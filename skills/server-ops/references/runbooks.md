# 운영 작업 절차 모음

SKILL.md 3절의 순서를 작업 종류별로 풀어 쓴 것이다. 프로젝트에 자체 스크립트(`deploy/scripts/*`)나 문서가 있으면 그 명령·경로·순서를 우선한다. 다만 승인 범위·비밀값 보호·연결 대상 확인·중단 조건은 SKILL.md를 따른다(SKILL.md 맨 앞 "우선순위").

## A. DB 마이그레이션 운영 배포: 사전 점검·백업·리허설
운영 배포(main push) 전에 한다. 이 단계에서는 운영 DB에 쓰지 않는다.

1. **사전 점검 SQL**: 이번 마이그레이션이 만들거나 지우는 객체(테이블·인덱스·컬럼·시드 행·권한 키)를 세는 `precheck.sql`을 서버의 작업 폴더(예: `~/<project>-release/`)에 저장하고 운영 DB에 실행한다. 기대값(적용 전)과 비교한다. 같은 SQL을 배포 후에도 다시 쓰므로 배포 후 기대값도 함께 적어 둔다.
2. **되돌리기 SQL**: 마이그레이션을 거꾸로 돌리는 `down.sql`을 만든다. `BEGIN; SET LOCAL lock_timeout='5s'; SET LOCAL statement_timeout='5min'; … COMMIT;` 형태로, 데이터 수정은 바뀐 값일 때만 되돌리도록 조건을 단다. 운영에서는 실행하지 않는다.
3. **덤프 백업**: 프로젝트 백업 스크립트로 날짜 붙은 폴더에 덤프한다. 덤프 끝부분(완료 표시)을 확인하고, `sha256sum *.sql.gz > SHA256SUMS`, 맥으로 `scp` 후 `shasum -a 256 -c SHA256SUMS`.
4. **복원 리허설**: 방금 덤프를 `<db>_rehearsal_YYYYMMDD` 같은 일회용 DB에 복원하고, 주요 테이블 건수를 운영과 비교한다.
5. **마이그레이션 리허설**: 리허설 DB에만 마이그레이션을 적용하고 걸린 시간을 잰다. 운영 `.env`의 접속 문자열은 화면에 내지 말고 변수로 읽어 DB 이름만 바꿔 쓴다.
6. **되돌리기 리허설**: 리허설 DB에 `down.sql`을 실행하고 `precheck.sql`이 적용 전 값으로 돌아오는지 확인한다.
7. **정리**: 리허설 DB 이름을 다시 확인하고 `DROP DATABASE`.
8. **앱 서버 백업**: 배포 폴더 밖 백업 폴더(권한 700)에 `.env`(권한 유지), 빌드 결과물, 업로드 볼륨(`docker run --rm -v <볼륨>:/data:ro … tar czf`)을 복사하고 파일 수를 기록한다.
9. **배포 전 화면 캡처**: 비교 도구가 있으면 운영 주소로 기준 캡처를 남긴다.

어느 단계든 기대와 다르면 거기서 멈추고 보고한다. 배포(main 병합·push)는 이 결과를 본 사용자의 승인 뒤에 따로 한다.

## C. 인증서 재발급·변경 (certbot + nginx)
1. 갱신 설정 파일을 `.bak-YYYYMMDD`로 백업. 복사 권한이 없으면 멈추고 보고한다(지시가 건너뛰기를 허용했으면 건너뛰고 기록).
2. `certbot certonly … --dry-run --non-interactive`. 실패하면 멈춘다.
3. 실제 발급은 `certonly`(설치기 아님, nginx 설정을 다시 쓰지 않게)로 같은 명령에서 `--dry-run`만 뺀다.
4. `nginx -t` 통과 후에만 `systemctl reload nginx`.
5. 도메인마다 `openssl s_client -servername <도메인>`으로 실제로 나가는 인증서의 SAN·만료일 확인, `certbot renew --dry-run --cert-name <이름>`으로 자동 갱신 확인.

## D. nginx에 새 사이트 추가
1. 같은 `server_name`이 이미 활성 설정에 있는지 먼저 확인한다.
2. 기존 파일을 고치지 않고 새 파일만 만든다(`sudo -n /usr/bin/tee`, 경로는 `command -v tee`로 확인).
3. `nginx -t` 통과 시에만 reload. 실패하면 새 파일을 지우고 reload하지 않는다.
4. 새 사이트 응답과 함께 같은 서버의 다른 사이트가 여전히 응답하는지 확인한다.

## E. 서비스 이전(cutover): 다른 서버나 자체 호스팅으로 옮기기
준비와 전환을 나눈다. **준비는 사용자 영향 없이 끝내고 멈춰서 보고, 전환은 사용자의 별도 승인 뒤에.**
- 준비: 새 쪽 스택을 기존과 분리해 띄움(별도 폴더·포트·새로 만든 비밀값, worker·예약 작업·메일 발송은 끈 채로, 운영 DB에 붙는지 실제 연결 대상 확인) → 기존 데이터를 읽기 전용으로 덤프해 새 쪽에 복원 리허설 → 실제 사용자가 기존 비밀번호로 로그인하고 데이터가 보이는지 터널로 확인 → 정기 백업(cron, 다른 서버로 사본, 보존 기간)을 설정하고 한 번 실행해 복원 시험.
- DB 밖 영속 데이터도 옮긴다: 업로드 볼륨·객체 저장소 버킷·인증서 등 목록을 만들고, 새 쪽으로 복사하거나 공유 유지 중 무엇으로 할지 정한다. 리허설에서 파일 수를 비교하고 실제 주소로 몇 개를 열어 확인한다.
- 전환 런북을 보고에 적는다: 쓰기 중지 → 최종 덤프·복원과 DB 밖 데이터의 최종 동기화(변경분) → 설정 전환(nginx·env) → 확인 → 롤백 방법(예: 이전 env로 재배포, DNS 원복).
- 롤백은 두 경우로 나눠 적는다. **쓰기 재개 전**이면 설정만 되돌리면 된다. **쓰기 재개 후**에는 새 쪽에 쌓인 데이터가 있으므로, 단순 원복은 그 데이터를 잃는다. 이 경우 새 데이터를 이전 쪽으로 옮기는 절차를 준비하거나, 잃어도 되는 범위를 전환 전에 사용자에게 확인받는다. 어느 쪽인지 정하지 않은 채로 전환을 진행하지 않는다.
- 기존 쪽(클라우드 등)은 며칠 동안 그대로 두어 롤백 경로로 쓴다.
- 비밀값·SMTP 계정 등 사용자만 줄 수 있는 것은 지어내지 말고 자리만 비워 두고 보고한다.
