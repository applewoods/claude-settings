# 테스트: 무엇을 어느 수준까지

> 언제 읽나: 새 API의 테스트를 쓸 때, 테스트 구조를 처음 잡을 때, 테스트는 통과하는데 운영에서 버그가 날 때.
> 원칙: 백엔드는 **통합 테스트(실제 DB + HTTP 계층)가 가장 가성비가 좋다.** 순수 로직만 단위 테스트로, 외부 경계만 계약 테스트로.

## 1. 범위 나누기
| 종류 | 대상 | 도구 | 비중 |
|---|---|---|---|
| 단위 | 계산·변환·검증 규칙, 권한 판정 함수, 프롬프트 조립 등 I/O 없는 함수 | pytest / Vitest | 로직이 복잡한 곳만 |
| 통합 | 엔드포인트 → 서비스 → **실제 PostgreSQL**까지 | FastAPI `TestClient`/`httpx.AsyncClient` + pytest, Next.js Route Handler는 핸들러 함수 직접 호출 + 테스트 DB | **대부분** |
| 계약 | 우리 API가 OpenAPI 문서와 일치하는지, 우리가 부르는 외부 API 응답 형식 가정 | Schemathesis(OpenAPI 기반 자동 생성), 외부 응답은 기록된 샘플로 파서 테스트 | 공개 API·분리 구성일 때 |
| E2E | 로그인 → 핵심 흐름 1~3개 | Playwright(프론트 스킬과 공유) | 최소한만 **[출시]** |

## 2. 통합 테스트를 실제 DB로 하는 이유
- SQLite·목(mock)으로 대신하면 PostgreSQL의 제약조건·트랜잭션·JSONB·대소문자 정렬·타임존 동작이 달라 **테스트는 통과하고 운영에서 깨진다.**
- 방법: Docker로 테스트용 PostgreSQL을 띄운다(`testcontainers` 또는 Compose의 `db-test` 서비스). 마이그레이션으로 스키마를 만든다(운영과 같은 경로를 검증하는 효과).
- 격리: 테스트마다 트랜잭션을 열고 끝나면 롤백하거나, 테이블을 비운다. 테스트끼리 데이터를 공유하면 순서에 따라 결과가 달라진다.
- 데이터는 팩토리 함수(`make_user()`, factory_boy 등)로 만든다. 실제 개인정보를 쓰지 않는다.

## 3. 모든 핵심 API에 최소한 이 다섯 가지
1. 정상 요청 → 기대한 상태 코드·응답 형식.
2. 잘못된 입력(필수 누락, 길이 초과, 잘못된 타입) → 422/400과 에러 형식.
3. 인증 없음 → 401.
4. **다른 사용자의 리소스 접근 → 403/404** (BOLA. 가장 중요한 보안 테스트).
5. 권한 없는 역할(일반 사용자가 관리자 기능) → 403.
- 4·5번은 역할 × 엔드포인트 표로 매개변수화(`pytest.mark.parametrize`)하면 엔드포인트가 늘어도 자동으로 따라간다.
- 상태 변경 API는 DB에 실제로 반영됐는지(그리고 실패 시 반영 안 됐는지)까지 확인한다. 응답만 보면 절반만 검증한 것이다.

## 4. 외부 의존성 다루기
- 외부 API·LLM은 테스트에서 실제로 부르지 않는다(느림, 비용, 비결정적). HTTP 계층에서 가짜 응답을 준다: Python `respx`(httpx용), `pytest-httpx`, Node `msw`.
- 가짜 응답에 **실패 경우도** 넣는다: 타임아웃, 429, 500, 형식이 깨진 JSON. 재시도·대체 동작은 여기서만 검증할 수 있다.
- 시간·난수에 의존하는 코드는 시계를 주입하거나 `freezegun`/`time-machine`으로 고정한다.
- 큐 작업은 작업 함수를 직접 호출해 테스트하고, "같은 작업 두 번 실행해도 결과가 같다"(멱등성)를 한 번 검증한다.
- LLM 출력 품질은 단위 테스트가 아니라 **평가 세트**로 따로 본다(`ai-features.md` 5절).

## 5. Next.js 서버 코드
- Route Handler는 `GET(request)` 함수를 직접 호출하거나 `next-test-api-route-handler` 같은 도구로 테스트한다 [확인 필요: Next.js 16 호환].
- Server Action은 액션 안의 로직을 일반 서버 함수(데이터 접근 계층)로 빼서 그 함수를 테스트하고, 액션은 "검증 + 권한 + 함수 호출"만 남긴다. 단, 추출한 함수만 테스트하면 액션의 검증·권한 호출이 빠져도 통과하므로 **액션 자체도** 잘못된 입력·비로그인·남의 리소스 3가지는 테스트한다(세션 함수를 대체해 액션을 직접 호출). 권한 검사를 데이터 접근 함수 안에 두면 이 누락 위험이 줄어든다.
- 인증이 필요한 테스트는 세션 조회(Better Auth `auth.api.getSession`)를 한 곳의 함수로 감싸 두고, 테스트에서는 그 함수를 대체한다.

## 6. 언제 무엇을 돌리나
- 로컬·커밋 전: 단위 + 통합(수십 초~2분 안에 끝나게 유지. 넘으면 아무도 안 돌린다).
- CI(GitHub Actions): 같은 테스트 + 린트·타입 검사(ruff, mypy/pyright, `tsc --noEmit`) + 의존성 취약점 검사. CI에서도 PostgreSQL 서비스 컨테이너로 같은 통합 테스트.
- 배포 직후: 운영에 스모크 테스트(헬스체크 + 읽기 전용 핵심 API 1~2개). 운영 데이터를 바꾸는 테스트는 돌리지 않는다.

## 7. 흔한 실수
- 커버리지 수치를 목표로 삼는 것: 80%여도 권한 테스트가 없으면 소용없다. "위 3절 다섯 가지가 핵심 API마다 있는가"가 더 좋은 기준이다.
- 구현 세부(내부 함수 호출 횟수)를 검증하는 목 남용: 리팩터링할 때마다 테스트가 깨진다. 입력과 결과(응답, DB 상태)를 검증한다.
- 테스트가 운영·개발 DB를 가리키는 것: 테스트 설정은 별도 `DATABASE_URL`을 쓰고, 운영 호스트면 시작 시 실패하게 가드를 둔다.
- "테스트가 통과했다"는 보고를 실행 없이 하는 것: 반드시 실제로 실행한 출력으로 확인한다.
