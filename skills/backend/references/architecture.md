# 아키텍처: 계층·비동기 작업·외부 호출

> 언제 읽나: 새 백엔드 프로젝트의 폴더 구조를 잡을 때, 오래 걸리는 작업·예약 작업을 넣을 때, 외부 API·LLM을 호출하는 코드를 쓸 때, "가끔 느려지거나 멈춘다"는 문제를 볼 때.

## 1. 계층 분리: 필요한 만큼만
| 규모 | 구조 |
|---|---|
| 데모·엔드포인트 10개 이하 | 라우터 함수 안에서 검증 → DB 호출 → 응답. 단, DB 세션·외부 클라이언트는 의존성으로 주입 |
| 그 이상, 또는 같은 로직을 API·워커·CLI에서 같이 씀 | `api/`(라우터: HTTP만) → `services/`(업무 규칙, 트랜잭션 경계) → `repositories/` 또는 ORM 직접(데이터 접근) |
- 판단 기준: **같은 업무 규칙이 두 군데에서 필요해지면** 서비스 계층으로 뺀다. 미리 만든 빈 계층은 이해만 어렵게 한다.
- 서비스 계층은 `Request`·`Response`·HTTP 상태 코드를 모르게 한다. 그래야 워커·테스트에서 그대로 쓴다.
- 트랜잭션 경계는 서비스(하나의 업무 단위)에 둔다. 라우터에서 commit을 여기저기 하면 절반만 저장되는 상태가 생긴다.
- 설정은 한 곳: FastAPI는 `pydantic-settings`로 환경변수를 타입 검증해서 읽고, **필수 값이 없으면 시작 시점에 실패**하게 한다(요청 처리 중에 터지는 것보다 낫다). Next.js는 서버 전용 값에 `NEXT_PUBLIC_`을 붙이지 않는다(붙이면 브라우저 번들에 들어간다).
- Next.js: DB·비밀값을 쓰는 코드는 `server-only`를 import한 데이터 접근 모듈에 모으고, 권한 확인도 거기서 한다.

## 2. FastAPI의 async 함정 (가장 흔한 성능 사고)
- `async def` 엔드포인트 안에서 **블로킹 호출**(`requests`, 동기 DB 드라이버, `time.sleep`, 큰 파일 읽기, CPU 연산)을 하면 이벤트 루프 전체가 멈춰 **모든 요청이** 느려진다.
- 판단: 쓰는 라이브러리가 async를 지원하면(`httpx.AsyncClient`, asyncpg, SQLAlchemy async) `async def`. 아니면 그냥 `def`로 선언하면 FastAPI가 스레드풀에서 돌린다. 섞어야 하면 `run_in_threadpool`/`asyncio.to_thread`.
- CPU를 수 초 이상 쓰는 작업(모델 추론, 대용량 전처리)은 웹 프로세스에서 하지 않는다. 별도 워커 프로세스(아래 큐)로.
- 외부 HTTP 클라이언트는 요청마다 만들지 말고 앱 시작 시 하나 만들어 재사용한다(lifespan). 커넥션 재사용이 안 되면 지연과 소켓 고갈이 생긴다.

## 3. 동기 처리 vs 백그라운드 작업 vs 큐
| 작업 성격 | 선택 |
|---|---|
| 1~2초 안에 끝나고 결과를 바로 보여 줘야 함 | 요청 안에서 동기 처리 |
| 응답 후 하면 되고, **유실돼도 괜찮음**(통계 기록, 캐시 갱신) | FastAPI `BackgroundTasks` / Next.js `after()`. 같은 프로세스에서 돌아서 재시작·배포 때 사라진다 |
| 유실되면 안 됨, 재시도 필요, 수십 초 이상, CPU·GPU 많이 씀 | **작업 큐 + 별도 워커 컨테이너** |
| 정해진 시각 반복 | 워커의 스케줄러(Celery beat, ARQ cron 등) 또는 호스트 cron이 내부 엔드포인트·CLI 호출. 웹 프로세스 안 스케줄러는 워커 수만큼 중복 실행된다 |

큐 고르기(Python 기준):
- 이미 Redis가 있거나 넣을 수 있음 → ARQ(async, 단순), RQ(동기, 단순), Celery(기능 많고 무거움: 복잡한 워크플로·대규모일 때만).
- 인프라를 늘리기 싫음 → PostgreSQL 기반 큐(`SELECT ... FOR UPDATE SKIP LOCKED`, 또는 Procrastinate 같은 라이브러리). 초당 수백 건 이하면 충분하다.
- 어떤 큐든 지킬 것: 작업은 **멱등**하게(최소 1회 전달이 기본이라 두 번 실행될 수 있다), 인자는 ID만 넘기고 데이터는 워커가 DB에서 다시 읽기, 작업별 타임아웃, 최대 재시도 후 실패 상태를 DB에 기록하고 알림.
- DB 저장과 작업 등록이 같이 성공해야 하면(주문 저장 + 메일 발송 작업) 트랜잭션 밖 등록은 한쪽만 성공할 수 있다. **[출시]** 아웃박스 패턴(같은 트랜잭션에 "보낼 작업" 행을 쓰고 워커가 가져감) 또는 PostgreSQL 큐로 같은 트랜잭션에 넣는다.

## 4. 외부 API·LLM 호출: 타임아웃·재시도·서킷 브레이커
**모든 외부 호출에 타임아웃을 명시한다.** 기본값을 믿지 않는다.
- Python `requests`는 기본 타임아웃이 **없다**(무한 대기). `httpx`는 기본 5초. Node의 `fetch`는 사실상 기본 제한이 길다 → `AbortSignal.timeout(ms)`를 건다.
- 타임아웃이 없으면 상대가 느려질 때 워커·커넥션이 전부 매달려 우리 서비스까지 죽는다(연쇄 장애).

타임아웃 시작값(근거: 상대 서비스의 정상 p99 지연보다 조금 크게 잡고, 우리 쪽 상위 타임아웃보다 작게):
| 호출 | 연결 | 전체(읽기) |
|---|---|---|
| 일반 내부·외부 REST | 2~5초 | 5~10초 |
| LLM 비스트리밍 | 5초 | 60~120초(출력 토큰 수에 비례; 긴 출력은 스트리밍이나 큐로) |
| LLM 스트리밍 | 5초 | 첫 토큰까지 10~30초, 토큰 사이 무응답 30~60초 |
- **타임아웃은 바깥이 안쪽보다 길어야 한다**: 리버스 프록시 > 앱 요청 처리 > 외부 호출 × 재시도 횟수. 반대면 프록시가 먼저 끊어 사용자는 실패를 보는데 서버는 계속 일한다.

재시도 규칙:
- **재시도해도 되는 것만**: 연결 실패, 타임아웃, `429`, `502/503/504`. `400/401/403/404/422`는 재시도해도 결과가 같다.
- POST 재시도는 상대가 멱등 키를 지원하거나 중복돼도 무해할 때만.
- 횟수: 사용자가 기다리는 요청은 최대 2~3회(총 대기 시간이 상위 타임아웃 안에 들어오게), 백그라운드 작업은 더 길게(수 분~수 시간 간격으로 5~10회).
- 간격: 지수 백오프 + 지터(예: 0.5s, 1s, 2s에 무작위 0~100% 가감). 지터가 없으면 모든 클라이언트가 같은 순간 다시 몰려 상대를 또 죽인다(AWS Architecture Blog "Exponential Backoff and Jitter").
- `429`/`503`에 `Retry-After`가 있으면 그 값을 따른다.
- 계층마다 재시도하면 곱해진다(SDK 2회 × 우리 코드 3회 × 프록시 = 폭증). **재시도는 한 계층에서만.** LLM SDK(OpenAI·Anthropic)는 기본 재시도가 있으니 [확인 필요: SDK 버전별 기본 횟수] 우리 코드에서 또 감싸지 않는다.
- 라이브러리: Python `tenacity`, `httpx` transport retries(연결 실패만), JS는 `p-retry` 등.

서킷 브레이커 **[출시]**, 외부 의존이 핵심 경로에 있을 때:
- 상대가 계속 실패하면 일정 시간 아예 호출하지 않고 즉시 대체 응답(캐시, "잠시 후 다시", 다른 모델)을 준다. 기다리다 같이 죽는 것을 막는다.
- 시작값: 최근 20~50건 중 실패율 50% 이상이면 열림 → 30~60초 후 1건 시험(half-open) → 성공하면 닫힘. 라이브러리(`pybreaker`, `opossum`) 사용.
- 데모·내부 도구는 타임아웃 + 제한된 재시도로 충분하다. 서킷 브레이커는 과하다.

## 5. 커넥션과 자원 한도
- DB 커넥션 수 = 웹 워커 수 × 풀 크기 + 워커 컨테이너 몫. 이 합이 PostgreSQL `max_connections`(기본 100)보다 넉넉히 작아야 한다. SQLAlchemy 기본 풀은 5 + overflow 10. 워커를 늘릴 때 같이 계산한다. 세부 튜닝은 `database` 스킬.
- uvicorn 워커 수: async 앱은 CPU 코어 수 정도에서 시작해 부하 테스트로 조정한다(`2×코어+1`은 동기 워커용 경험칙). 컨테이너 하나에 워커 여러 개(`--workers`)도 되고, 컨테이너를 여러 개 띄워도 된다.
- 요청 본문 크기 제한은 리버스 프록시에서 먼저(Nginx `client_max_body_size`, Caddy `request_body max_size`).

## 6. Next.js + FastAPI 분리 구성
- 브라우저 → Caddy → (`/` Next.js, `/api/ai/*` FastAPI)처럼 **같은 도메인 경로 분기**가 가장 단순하다(CORS 불필요, 쿠키 공유).
- Next.js 서버가 FastAPI를 부르는 경우 내부 네트워크 주소(`http://api:8000`)로 부르고, FastAPI 포트는 외부에 열지 않는다. 서버 간 호출은 공유 비밀이나 짧은 서명 토큰으로 인증한다(`auth-security.md` 2절).
- 타입 공유: FastAPI OpenAPI에서 TS 타입을 생성(`openapi-typescript` 등)해 손으로 맞추지 않는다.
