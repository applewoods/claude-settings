# 관찰 가능성: 로그·지표·추적·헬스체크·알림

> 언제 읽나: 새 서비스의 로그를 설정할 때, 배포 전에 운영 준비를 할 때, "가끔 에러가 난다·느리다"를 조사할 때.
> 단계별 최소선: **데모** = 구조화 로그 + 헬스체크. **내부** = + 에러 추적(Sentry 등) + 외부 업타임 감시. **출시** = + 지표 대시보드 + 알림 + (서비스가 여러 개면) 분산 추적.

## 1. 로그
- **구조화 로그(JSON 한 줄)**로 표준출력에 쓴다. 파일에 직접 쓰지 않는다(컨테이너는 stdout을 모은다). Python: `structlog` 또는 표준 `logging` + JSON 포매터, Node: `pino`.
- 모든 요청 로그에 넣을 필드: `timestamp`(UTC), `level`, `request_id`, `user_id`(있으면, 이메일 말고 ID), `method`, `path`(쿼리 문자열 제외 또는 마스킹), `status`, `duration_ms`. LLM 호출이면 `model`, `input_tokens`, `output_tokens`, `cost` 추정(`ai-features.md`).
- `request_id`: 리버스 프록시나 미들웨어에서 생성(`X-Request-ID`가 오면 이어받기), 응답 헤더와 에러 본문에도 넣고, 워커로 넘기는 작업 인자에도 넣는다. 이 하나로 사용자 문의 → 로그 → 워커까지 이어진다.
- 레벨 기준: `ERROR` = 사람이 봐야 함(알림 대상), `WARNING` = 이상하지만 처리됨(재시도 성공, 4xx 급증), `INFO` = 요청·작업 단위 1줄, `DEBUG` = 운영에서 끔. 4xx를 ERROR로 찍으면 알림이 쓸모없어진다.
- **찍지 않는 것**: 비밀번호, 토큰, 쿠키, `Authorization` 헤더, API 키, 전체 요청·응답 본문, 개인정보(이메일·전화·주민번호), 사용자 프롬프트 원문(필요하면 별도 동의·보관 기간 정책으로 분리). 로거에 마스킹 필터를 둔다.
- 예외는 스택트레이스와 함께 한 번만 기록한다(잡을 때마다 다시 찍으면 같은 에러가 다섯 줄).
- **Docker 로그 보관**: 기본 `json-file` 드라이버는 회전하지 않아 디스크가 찬다. Compose에 `logging: {driver: json-file, options: {max-size: "10m", max-file: "5"}}`를 넣거나 데몬 기본값을 설정한다. 자체 서버 장애 원인 1순위가 "디스크 가득 참"이다.

## 2. 에러 추적
- 내부 이상: Sentry(SaaS 무료 플랜 또는 자체 호스팅) 같은 에러 추적 도구를 붙인다. 로그 검색보다 "새 에러 종류가 생겼다"를 훨씬 빨리 안다.
- 보낼 때 개인정보 필터(`send_default_pii=False` 기본 유지)와 환경 태그(`production`/`staging`), 릴리스 버전(git SHA)을 붙인다. 어느 배포에서 생긴 에러인지 바로 보인다.

## 3. 지표 [출시]
- 서비스 지표는 **RED**: 요청 수(Rate), 에러율(Errors), 지연(Duration, 평균 말고 **p50/p95/p99**). 평균은 느린 소수를 숨긴다.
- 자원 지표는 **USE**: CPU·메모리·디스크·DB 커넥션의 사용률, 포화(대기열 길이), 에러.
- 추가로 볼 것: 큐 길이·가장 오래된 작업 나이, 외부 API·LLM 호출 실패율과 지연, 일별 LLM 비용.
- 도구: 단일 서버면 Prometheus + Grafana(+ node-exporter, cAdvisor)가 표준. 가볍게 가려면 Netdata 같은 올인원, 또는 Grafana Cloud 무료 플랜. FastAPI는 `prometheus-fastapi-instrumentator` 등으로 `/metrics` 노출(외부 공개 금지).
- 경로 라벨에 실제 ID를 넣지 않는다(`/users/123` ✕ → `/users/{id}`). 라벨 종류가 폭증하면 Prometheus가 느려진다.

## 4. 분산 추적 [출시, 서비스가 2개 이상일 때]
- Next.js → FastAPI → 워커 → LLM처럼 한 요청이 여러 프로세스를 지나면 OpenTelemetry로 추적을 붙인다. 어디서 시간이 걸렸는지 한 화면에 보인다.
- 서비스 하나짜리면 `request_id` 로그로 충분하다. 추적 인프라(Tempo, Jaeger)를 먼저 깔지 않는다.
- LLM 호출 추적은 Langfuse 같은 LLM 전용 관찰 도구가 프롬프트·토큰·비용을 함께 보여 줘서 편하다(자체 호스팅 가능) [도입 시 개인정보 정책 확인].

## 5. 헬스체크
| 종류 | 경로 예 | 검사 내용 | 쓰는 곳 |
|---|---|---|---|
| liveness(살아 있나) | `/healthz` | 프로세스가 응답하는지만. **DB·외부 API를 검사하지 않는다** | Docker `HEALTHCHECK`, 재시작 판단 |
| readiness(받을 준비 됐나) | `/readyz` | DB 연결(`SELECT 1`), 필수 의존성, 마이그레이션 완료 | 배포 시 트래픽 전환 판단, `depends_on: condition: service_healthy` |
- liveness에 DB 검사를 넣으면 DB가 잠깐 느릴 때 앱 컨테이너가 전부 재시작돼 장애가 커진다.
- 외부 API·LLM 상태는 readiness에도 넣지 않는다(상대가 죽으면 우리도 "준비 안 됨"이 되어 전체가 내려간다). 대신 지표·알림으로 본다.
- 헬스체크 응답에 버전(git SHA)을 넣으면 "지금 뭐가 배포돼 있나"가 바로 보인다. 내부 정보(DB 호스트 등)는 넣지 않는다.

## 6. 알림
- 원칙: **사용자가 겪는 증상**에 알린다(에러율, 지연, 사이트 다운). 원인 지표(CPU 80%)에 일일이 알리면 무시하게 된다. 예외는 디스크·인증서처럼 미리 알아야 하는 것.
- 최소 알림 세트:
  - 외부 업타임 감시(서버 **밖**에서): UptimeRobot, Better Stack, 또는 다른 서버의 Uptime Kuma. 서버가 죽으면 서버 안 감시도 같이 죽는다. 1~5분 간격.
  - 5xx 비율이 5분간 일정 수준 이상(예: 1~5%, 트래픽에 맞춰 조정).
  - p95 지연이 평소의 2~3배 이상 10분 지속.
  - 디스크 사용률 80% 이상.
  - 큐의 가장 오래된 작업이 기준 시간 초과.
  - 백업 작업 실패 또는 24시간 이상 성공 기록 없음.
  - LLM 일 비용이 예산의 80% 도달.
  - TLS 인증서 만료 14일 전(Caddy 자동 갱신이어도 갱신 실패를 잡으려고).
- 알림마다 "받으면 무엇을 하는가"를 한 줄로 적는다(런북). 할 일이 없는 알림은 지운다.
- 받는 곳: 혼자·소규모면 이메일 + 메신저(Slack·Discord·텔레그램 웹훅)로 충분하다.
