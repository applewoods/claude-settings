# LLM 기능을 백엔드에 붙일 때

> 언제 읽나: 챗봇·요약·추출·RAG·에이전트 기능 등 LLM 호출이 들어가는 API를 만들 때, LLM 비용·지연·실패가 문제일 때.
> 모델 ID·가격·파라미터는 자주 바뀐다. Claude를 쓰면 `claude-api` 스킬로, 다른 공급자는 공식 문서로 **그때그때 확인**한다. 여기에는 공급자와 무관한 판단 기준만 적는다. 벡터 검색·임베딩 저장은 `database` 스킬.

## 1. 구조 원칙 [모두]
- **LLM 호출은 백엔드에서만.** 브라우저·앱에 API 키를 두지 않는다. 프론트는 우리 API를 부른다.
- 공급자 호출을 얇은 어댑터 한 곳(`llm/client.py`)에 모은다. 모델 ID·타임아웃·재시도·로깅·비용 계산이 한 곳에 있어야 모델 교체·장애 대응이 쉽다. 무거운 추상화 프레임워크는 필요할 때만.
- 모델 ID는 코드에 흩지 말고 설정값으로. 용도별로 나눈다(예: `MODEL_FAST`, `MODEL_SMART`).
- LLM 출력은 **신뢰할 수 없는 입력**이다(OWASP API10, LLM Top 10의 프롬프트 주입·부적절한 출력 처리). 그대로 HTML 렌더·SQL·셸·권한 판단에 쓰지 않는다.

## 2. 지연 관리
| 상황 | 방식 |
|---|---|
| 사용자가 보고 있는 대화·생성 | **스트리밍(SSE)**. 첫 토큰이 1~2초 안에 보이면 전체가 20초여도 견딘다 |
| 구조화된 결과(JSON)만 필요, 수 초 내 | 비스트리밍 + 로딩 표시 |
| 수십 초 이상, 여러 단계, 일괄 처리 | 큐 작업 + 상태 조회(`architecture.md` 3절). 공급자의 Batch API는 보통 비용이 크게 싸다(지연 허용 시) [확인 필요: 공급자별 할인율] |
- 스트리밍 구현 체크:
  - FastAPI `StreamingResponse`(`media_type="text/event-stream"`), Next.js Route Handler에서 `ReadableStream` 반환. Server Action은 장시간 스트리밍에 맞지 않는다.
  - 리버스 프록시 버퍼링 확인(Caddy는 SSE 자동 플러시, Nginx는 `X-Accel-Buffering: no`; `deployment.md` 3절).
  - **클라이언트가 연결을 끊으면 공급자 호출도 취소한다.** 안 하면 아무도 안 보는 응답에 토큰 비용을 낸다(FastAPI는 `request.is_disconnected()` 확인 또는 취소 전파, Node는 `request.signal`을 SDK에 전달).
  - 스트림 중간 실패를 처리한다: 이미 200을 보냈으므로 HTTP 상태로 알릴 수 없다. 에러 이벤트(`event: error`)를 정의한다.
  - 완료 후 전체 응답·토큰 사용량을 DB에 저장하는 것은 스트림이 끝난 뒤 한 번에.
- 프롬프트 앞부분(시스템 프롬프트, 고정 문서)을 고정하고 뒤에 가변 내용을 두면 공급자의 프롬프트 캐싱으로 지연·비용이 함께 줄어든다(공급자별 조건 확인).

## 3. 비용 관리
- **모든 호출을 기록**한다: `request_id`, `user_id`, 기능명, 모델, 입력·출력 토큰, 캐시 토큰, 지연, 성공 여부, 추정 비용. 이게 없으면 "왜 이번 달 청구가 3배인가"에 답할 수 없다.
- 한도 [내부부터]: 사용자별·기능별 일/월 토큰 또는 비용 한도, 요청당 입력 길이 상한(검증 단계에서 자름), `max_tokens` 명시. 공급자 콘솔에도 계정 지출 한도를 건다(이중 안전장치).
- 무료·익명 사용이 열린 출시 서비스는 봇의 비용 공격 대상이다: 로그인 필수, 강한 레이트 리밋, 일일 전체 예산 차단기(넘으면 기능 일시 중지 + 알림).
- 비용 줄이는 순서(효과 큰 순, 경험칙): (1) 작은 모델로 충분한 작업은 작은 모델로, (2) 프롬프트 캐싱, (3) 같은 입력의 결과 캐시(입력 해시 + 모델 + 프롬프트 버전을 키로), (4) 컨텍스트 줄이기(RAG 검색 결과 개수·길이), (5) 지연 허용 작업은 Batch.
- 응답 캐시는 개인화·최신성이 필요한 답에는 쓰지 않는다. 다른 사용자의 데이터가 섞인 응답을 캐시 키 실수로 공유하면 정보 유출이다.

## 4. 실패 처리
- 실패 유형별 대응:
| 유형 | 대응 |
|---|---|
| 429(레이트 리밋)·529/503(과부하) | `Retry-After` 따라 백오프 재시도(SDK 내장 재시도 확인 후 중복 금지). 계속되면 대체 모델 또는 "잠시 후 다시" |
| 타임아웃 | 사용자 요청이면 1회 재시도 후 실패 안내, 큐 작업이면 백오프 재시도 |
| 400(컨텍스트 초과, 잘못된 파라미터) | 재시도 금지. 입력을 줄이거나 버그 수정 |
| 안전 정책 거부·빈 응답 | 재시도해도 같은 경우가 많다. 사용자에게 사유를 일반화해 안내 |
| 구조화 출력 파싱 실패 | 스키마 검증(Pydantic/Zod) → 실패 시 에러 내용을 붙여 **1회만** 재요청 → 그래도 실패면 실패 처리. 공급자의 구조화 출력·도구 호출 기능을 쓰면 크게 줄어든다 |
- 대체(fallback) 모델은 출력 형식·품질이 다를 수 있으니 같은 평가 세트로 확인한 뒤에만 쓴다.
- 사용자에게 "AI 오류"라고만 하지 말고, 다시 시도 가능 여부와 입력이 저장됐는지를 알린다(화면 문구는 `ux-ui-design` 스킬).

## 5. 프롬프트 버전 관리와 평가
- 프롬프트는 코드다: 문자열을 코드 곳곳에 흩지 말고 `prompts/` 폴더의 파일(템플릿)로 두고 깃으로 관리한다. 각 프롬프트에 이름과 버전(`summarize@v3`)을 붙인다.
- 호출 기록에 프롬프트 버전을 남긴다. 품질 불만이 들어오면 어느 버전 결과인지 알아야 한다.
- 프롬프트·모델을 바꾸기 전에 **평가 세트**로 비교한다: 실제 입력 대표 사례 20~100개 + 기대 결과(또는 채점 기준). 자동 채점(정확 일치, 스키마 통과, LLM 채점) + 일부 사람 확인. 바꿀 때마다 같은 세트로 돌려 이전 버전과 비교한다. 연구 맥락의 평가 설계는 `data-analysis` 스킬.
- 운영 프롬프트를 콘솔·DB에서 바로 고치는 구조는 출시 서비스에서만, 그것도 버전 기록과 롤백이 될 때만.

## 6. 보안: 프롬프트 주입과 도구 권한
- 사용자 입력·검색 문서·웹페이지·업로드 파일 안의 지시문은 모델을 조종할 수 있다(간접 프롬프트 주입). **완벽한 방어는 없다**는 전제로 설계한다.
- 그래서 모델에 주는 **도구 권한을 최소화**한다: 읽기 전용 도구 우선, 쓰기·삭제·발송·결제 도구는 사용자 확인 단계를 거친다. 도구 실행 시 권한 검사는 모델이 아니라 **서버가** 현재 사용자 기준으로 한다(모델이 준 `user_id`를 믿지 않는다).
- RAG에서 검색 대상은 현재 사용자가 볼 수 있는 문서로 쿼리 단계에서 제한한다. 검색 후 모델에게 "이건 보여 주지 마"라고 지시하는 것은 보안이 아니다.
- URL을 가져오는 도구는 SSRF 방어 필수(`auth-security.md` 1절 API7).
- 시스템 프롬프트에 비밀값·내부 정보를 넣지 않는다. 언젠가 새어 나온다고 가정한다.
- 개인정보: 공급자의 데이터 보존·학습 사용 정책을 확인하고, 필요한 경우 민감 정보를 마스킹한 뒤 보낸다. 연구 데이터라면 IRB·데이터 사용 동의 범위도 확인한다 [프로젝트별 확인].
