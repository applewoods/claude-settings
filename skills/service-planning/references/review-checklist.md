# 기획 검토 체크리스트

언제 읽나: 기획 완료 전 자체 점검, 사용자가 기존 기획 검토를 요청했을 때, verifier·Codex 검증 브리핑을 쓸 때. 유형별로 해당 없는 항목은 "해당 없음 — 이유"로 표시한다.

## 판정 방식
- 항목마다 통과 / 보완 필요 / 해당 없음. "보완 필요"에는 **무엇을 어떻게** 고칠지 한 줄.
- 심각도: 치명(이대로면 만들 이유가 없거나 법적 위험) / 중요(개발·디자인이 추측해야 함) / 개선.
- 결론을 먼저: "이대로 개발 착수 가능 / 조건부 / 다시 기획" + 치명·중요 상위 3개.

## A. 문제·가치 (치명 후보)
- [ ] 문제 진술에 해결책 단어가 없고, 실제 사례나 근거가 있다(없으면 `[가정]`).
- [ ] 우선 타깃이 하나로 정해져 있고, 사용자와 구매·승인자가 다르면 둘 다 적혀 있다.
- [ ] 현재 대안(비소비·범용 AI 포함) 대비 차이가 구체적이다("편리함" 아님).
- [ ] 범용 AI로 대체 가능한지 판단과 근거가 있다.
- [ ] 경쟁·대안 조사에 출처(URL, 확인일)가 있고, 확인 못 한 수치는 `[확인 필요]`다.

## B. 가정·검증
- [ ] 가장 위험한 가정 1~3개가 명시돼 있고, MVP가 그것을 검증하도록 설계돼 있다.
- [ ] 검증 계획에 실행 전 성공·실패 기준이 있다.
- [ ] 가상 사용자·지인 반응을 수요 근거로 쓰지 않았다.

## C. 지표
- [ ] North Star가 가치를 얻은 순간을 센다(누적·허영 지표 아님).
- [ ] 지표마다 정의·측정 이벤트·기준선(또는 `[가정]`)·목표가 있다.
- [ ] 가드레일과 중단 기준이 있다.

## D. 범위·요구사항 (중요 후보)
- [ ] MVP가 핵심 여정 하나를 끝까지 잇는다. Must가 절반을 넘지 않는다.
- [ ] 범위 밖 목록이 있다.
- [ ] Must 스토리마다 확인 가능한 수용 기준이 있다("빠르게", "쉽게" 같은 말이 없다).
- [ ] 핵심 화면마다 빈·로딩·오류·권한 거부 상태가 정해져 있다.
- [ ] 비기능 요구사항 칸이 채워져 있다(성능, 접근성, 지원 기기·브라우저, 보안, 데이터 보관·백업).
- [ ] 역할·권한(누가 무엇을 보고 고칠 수 있나)이 정의돼 있다.
- [ ] 모바일 웹과 앱의 차이(푸시, 접근권한, 스토어 심사, 오프라인)가 적혀 있다.

## E. 개인정보·법규 (치명 후보)
- [ ] 수집 항목표(목적·근거·필수/선택·보관 기간·위탁/제공처)가 있고, 목적 없는 항목이 없다.
- [ ] `privacy-kr.md` 3절 플래그를 모두 확인했다(14세 미만, 민감정보, 국외 이전/LLM, 광고성 정보, 접근권한, 위치, 자동화된 결정, 생성형 AI 고지).
- [ ] 계정 삭제·권리 행사 경로가 화면 흐름에 있다.
- [ ] 출시 서비스는 전문가 확인이 출시 조건에 들어 있다.

## F. AI 기능 (있을 때)
- [ ] AI/일반 로직/사람 확인의 경계가 표로 있다.
- [ ] 평가셋과 합격 기준이 있다.
- [ ] 실패·지연·틀림 UX와 요청당 비용이 정해져 있다.

## G. 넘기기
- [ ] 결정 기록(무엇을, 왜, 버린 대안)과 열린 질문(담당, 기한)이 있다.
- [ ] `[가정]`이 남아 있으면 사용자 확인을 받았다.
- [ ] 문서 간 모순이 없다(PRD 기능 ↔ 유저 스토리 ↔ 화면 목록 ↔ MVP 표의 이름·범위가 일치).
- [ ] 목업이 화면 목록과 일치하고 모바일 폭에서 확인됐다.
- [ ] 측정 이벤트 목록이 개발 범위에 들어 있다.

## 유형별 최소 통과선
- 연구 데모: A(한 문단 수준), C(시연 성공 기준), D(핵심 시나리오·오류 상태), E(실데이터 쓸 때), F, G.
- 내부 도구: A~G 전부, B는 핵심 1~2개.
- 사이드·출시 서비스: 전부. 출시 서비스의 E 치명 항목이 하나라도 남으면 "다시 기획".
