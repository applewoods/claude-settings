# 범위·우선순위 (MVP)

언제 읽나: 7단계에서 MVP 범위를 정할 때, "이 기능 넣을까" 판단할 때, `docs/mvp.md`를 쓸 때.

## 1. MVP의 정의
MVP는 **가장 위험한 가정을 검증하면서 우선 타깃이 실제 가치를 한 번 끝까지 받을 수 있는 최소 범위**다.
- "기능을 다 얕게"가 아니라 "핵심 여정 하나를 끝까지". 예: 기록 → 정리 → 공유 중 공유가 핵심이면 셋 다 최소로라도 이어져야 한다.
- 품질을 낮추는 것이 아니다. 범위를 좁히고, 그 범위의 품질(오류 처리, 속도, 신뢰)은 지킨다.
- 손으로 해도 되는 것은 자동화하지 않는다(관리자 기능, 정산, 콘텐츠 검수는 초기엔 사람이 수작업).

## 2. 절단 순서
1. 핵심 여정(우선 타깃이 가치를 얻기까지의 단계)을 5~7단계로 적는다.
2. 단계마다 "이게 없으면 여정이 끊기나?" — 끊기면 Must.
3. 가장 위험한 가정 검증에 필요한가? — 필요하면 Must.
4. 나머지는 Should/Later. **범위 밖 목록**에 명시적으로 적는다(안 적으면 다시 들어온다).
5. Must 판별: 위 2·3번에 더해 **법적·안전 필수**(아래 목록)도 Must다. 셋 다 아니면 Should 이하.
6. 범위의 최종 크기는 일정·인력·노력 추정으로 정한다. Must 비율은 후보 개수에 따라 달라지므로 기준이 아니라 **경고 신호**로만 본다(Must가 대부분이면 2·3번 질문을 더 엄격히 다시 묻는다).

기본으로 MVP 밖에 두고 시작할 후보(필요성을 증명하면 들인다): 소셜 로그인 여러 개, 다국어, 다크 모드, 관리자 대시보드, 상세 설정, 결제(초기엔 수동 청구·무료), 알림 세부 설정.
법적·안전 필수 — 해당 조건이면 MVP라도 빼지 않는다(Must): 개인정보를 수집하면 동의·처리방침, 계정이 있으면 계정 삭제(앱은 스토어 정책상 요구될 수 있음 `[확인 필요]`), 사용자 데이터를 저장하면 백업, 실사용자를 받으면 측정 이벤트, 항상 기본 오류 처리. 계정·개인정보·저장이 없는 연구 데모는 해당 항목이 "해당 없음"이다.

## 3. 점수 도구와 한계
| 도구 | 방식 | 쓸 때 | 한계 |
|---|---|---|---|
| MoSCoW | Must/Should/Could/Won't 분류 | 이해관계자와 범위 합의 | 기준이 없으면 전부 Must. 위의 절단 질문을 기준으로 쓴다 |
| RICE | (Reach × Impact × Confidence) ÷ Effort | 비슷한 크기의 후보 여러 개 비교 | 초기 서비스는 Reach·Impact가 전부 추정이라 정밀해 보이는 착시. Confidence를 정직하게 낮춘다 |
| ICE | Impact × Confidence × Ease | 빠른 실험 우선순위 | 주관적. 같은 사람이 한 번에 매겨야 비교 가능 |
| Kano | 기본/성능/매력 요소 분류 | 무엇이 "없으면 불만"인지 구분 | 설문이 필요하고 시간이 지나면 매력→기본으로 이동 |
| 가치 × 노력 2×2 | 빠른 승리/큰 베팅/채우기/함정 | 회의에서 빠르게 | 노력 추정이 낙관적으로 쏠림 |

- 점수는 토론을 구조화하는 도구다. 점수 1등을 기계적으로 고르지 않는다. 전략(우선 타깃, 위험 가정)에 안 맞으면 점수가 높아도 뺀다.
- 점수에 쓴 추정치마다 근거나 `[가정]`을 적는다.
- 의존 관계(로그인 없이 공유 불가 등)는 점수와 별개로 순서를 정한다.

## 4. 단계 계획
| 단계 | 목표(검증할 가정) | 포함 범위 | 넘어갈 조건(지표) |
|---|---|---|---|
| 0 검증 | 수요 가정 | 랜딩·컨시어지 | 사전 등록 X% |
| 1 MVP | 핵심 여정 가치 | Must | 첫 가치 도달률 X%, 4주 잔존 Y% |
| 2 확장 | 반복 사용·확산 | Should 일부 | ... |
- 기간은 추정치임을 밝힌다. 연구 데모는 데모 날짜에서 거꾸로 계획하고, 마지막 20%를 리허설·버그 수정용으로 비워 둔다.

## 5. 흔한 실수
- 경쟁사에 있는 기능이라 Must로 둔다 → 우리 우선 타깃·위험 가정과 연결이 없으면 Later.
- 내가 만들고 싶은(기술적으로 재미있는) 기능을 Must로 둔다.
- 범위 밖 목록이 없다 → 개발 중 범위가 계속 늘어난다.
- "나중에 쉽게 붙일 수 있다"고 가정한다 → 권한 구조·데이터 모델·다국어·결제는 나중에 붙이기 어렵다. 지금 안 만들어도 **구조 결정**은 PRD 결정 기록에 남긴다.
