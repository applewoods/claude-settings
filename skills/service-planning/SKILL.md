# 서비스 기획 매뉴얼

> **팀으로 진행:** 여러 단계이거나 검증이 중요한 일은 `team-orchestration` 스킬의 "서비스 기획" 팀 구성(scout·builder·expert·verifier)으로 나눠 맡긴다. 각 팀원은 이 매뉴얼을 따른다.

기획의 일은 문서를 채우는 것이 아니라 **만들 가치가 있는지, 무엇을 빼는지, 무엇으로 성공을 판단하는지** 정하는 것이다. 기능 목록은 맨 마지막에 나온다.

## 0. 유형 판별 — 깊이를 먼저 정한다
기획 시작 때 유형을 정해 PRD 맨 위에 적는다. 모르면 `[가정]`으로 두고 진행한다.

| 단계 | 연구 데모 | 내부 도구 | 사이드 프로젝트 | 출시 서비스 |
|---|---|---|---|---|
| 1 문제·가치 | 한 문단 | 필수 | 필수 | 필수 |
| 2 경쟁·대안 조사 | 관련 연구·데모 3개 | 기존 방식(엑셀 등) 비교 | 필수 | 필수 |
| 3 가정 지도·검증 | 생략 | 핵심 1~2개 | 필수 | 필수 |
| 4 가상 사용자 조사 | 생략 | 선택 | 권장 | 권장 |
| 5 지표 | 시연 시나리오 성공 기준 | 업무 시간·오류 감소 | 필수 | 필수 + 가드레일 |
| 6 개인정보·법규 | 실데이터 쓰면 필수 | 필수 | 필수 | 필수 + 전문가 확인 |
| 7 출시·실험 계획 | 생략 | 시범 부서 | 간단히 | 필수 |
| 산출물 | 전부, 양식의 ★ 절만 | 전부 | 전부 | 전부 |

- 연구 데모는 **시연에서 보여줄 것**과 **보여주지 않을 것**이 범위다. 회원가입·결제·관리자 화면은 기본으로 범위 밖.
- 유형이 바뀌면(데모 → 출시) 생략한 단계를 다시 한다. 데모 때 만든 가정을 그대로 출시 근거로 쓰지 않는다.

## 진행 방식: 초안 먼저
1. 내가 아이디어를 주면 빈 곳을 묻기 전에 **합리적인 가정으로 초안부터** 만든다.
2. 가정한 부분은 `[가정]`으로 표시해서 내가 고치기 쉽게 한다.
3. 정말 판단이 안 서는 핵심 질문만 초안 끝에 3개 이내로 모아서 묻는다. 고르는 기준: **답에 따라 범위나 대상이 바뀌는 질문**만. 문구·색·세부 기능은 묻지 않고 가정한다.

## 1. 문제·대상·가치 정의
읽을 것: `references/problem-and-value.md`
- 문제 진술 한 문장: "[누가] [어떤 상황에서] [무엇을 하려는데] [무엇 때문에] 못 한다/힘들다. 지금은 [대안]으로 버틴다."
- 해결책이 들어간 문제 진술("~ 앱이 없다")은 문제가 아니다. 다시 쓴다.
- 대상은 세분화한 뒤 **우선 타깃 하나**를 고른다. 기준: 고통이 크고 자주 겪고, 지금 대안에 돈·시간을 쓰고 있고, 우리가 닿을 수 있는 집단.
- 가치 제안은 **현재 대안 대비** 무엇이 나은지로 쓴다. "편리하다"는 차별점이 아니다.

## 2. 경쟁·대안 조사 (웹)
- 웹 검색으로 비슷한 서비스 3~5개 + **비소비 대안**(엑셀, 카톡, 종이, 그냥 참기) + **범용 AI**(ChatGPT·Claude 등에 직접 묻기)를 비교한다. 확인한 출처(URL, 확인 날짜)를 적는다.
- 판단 질문: "사용자가 범용 AI에 한 번 물어보면 끝나는 일인가?" 그렇다면 차별점은 데이터·맥락 축적, 워크플로 통합, 신뢰·책임 중 무엇인지 적는다. 답이 없으면 기획을 다시 본다.
- 경쟁사 기능을 표로 나열만 하지 않는다. 그들이 **누구를 버렸는지**(가격, 복잡도, 특정 상황)가 기회다.

## 3. 가정 지도 → 가장 위험한 가정부터
읽을 것: `references/validation.md`
- 가정을 수요(원하는가)·사용성(쓸 수 있는가)·실현성(만들 수 있는가)·사업성(지속 가능한가)으로 나누고, **틀리면 치명적 × 근거가 약한** 것부터 1~3개 검증한다.
- 검증 계획마다 성공·실패 기준을 **실행 전에** 숫자로 적는다. 결과를 본 뒤 기준을 바꾸지 않는다.

## 4. 가상 사용자 사전 조사 (선택, 권장)
- 초안을 만든 뒤 실제 사용자 조사 전에, `synthetic-user-research` 스킬로 페르소나에게 사전 질문을 해서 시나리오·불편함·이탈 이유를 찾는다. 인원·절차는 그 스킬을 따른다.
- 결과는 `[가설]`이다. 수요·가격·우선순위 판단의 근거로 쓰지 않는다. 실제 사용자 5명 내외 인터뷰로 확인한 것만 PRD에 확정 반영하되, 5명 인터뷰는 **문제·사용성 발견용**이지 수요 검증이 아니다(수요는 3단계의 행동 기반 검증으로).

## 5. 성공 지표
읽을 것: `references/metrics.md`
- North Star 1개 + 선행 지표 2~3개 + 가드레일 1~2개. 각 지표에 정의(분자/분모/기간), 기준선, 목표, 측정 이벤트를 적는다.
- 가입자 수·다운로드·페이지뷰 같은 누적 지표를 North Star로 쓰지 않는다. **사용자가 가치를 얻은 순간**을 센다.
- 출시 전에 "이 수치 아래면 접거나 방향을 바꾼다"는 중단 기준을 적는다.

## 6. 개인정보·보안·법규
읽을 것: `references/privacy-kr.md` (AI 기능이 있으면 `references/ai-features.md`도)
- 수집 항목마다 목적·법적 근거·보관 기간·접근자를 표로 적는다. 목적에 연결되지 않는 항목은 뺀다.
- 플래그: 만 14세 미만 이용 가능성, 민감정보(건강 등), 위치정보, 외부 API(특히 해외 LLM)로 개인정보 전송, 광고성 알림, 결제. 하나라도 있으면 PRD의 "법규 검토 필요" 칸에 올린다.
- 출시 서비스는 이 매뉴얼의 점검으로 끝내지 않는다. 법적 판단은 `[확인 필요]`로 두고 전문가 확인을 출시 조건에 넣는다.

## 7. 범위·우선순위 (MVP)
읽을 것: `references/prioritization.md`
- 원칙: **핵심 여정 하나를 처음부터 끝까지** 잇는 것이 MVP다. 기능을 고루 얕게 만드는 것이 아니다.
- Must 판별(셋 중 하나라도 "예"면 Must, 아니면 Should 이하): ① 없으면 핵심 여정이 끊기나? ② 없으면 3단계의 가장 위험한 가정을 검증할 수 없나? ③ 법적·안전 필수인가(동의·처리방침, 계정 삭제, 기본 오류 처리, 측정 이벤트, 백업)?
- 범위의 최종 크기는 일정·인력·노력 추정으로 정한다. Must가 많아 보이면 ①②를 더 엄격히 다시 묻는다.
- RICE·MoSCoW 점수는 토론 도구다. 점수가 결정을 대신하지 않고, 점수에 쓴 추정치의 근거를 함께 적는다.

## 8. 요구사항 작성
양식: `templates/prd.md`, `templates/user-stories.md`, `templates/screens.md`, `templates/mvp.md`
- 모든 Must 스토리에 **수용 기준**(Given/When/Then, 확인 가능한 문장)을 단다. "빠르게", "쉽게"는 숫자나 관찰 가능한 행동으로 바꾼다.
- 화면마다 기본 외에 **빈 상태·로딩·오류·권한 거부·오프라인** 상태를 정한다. 빠지면 개발자가 추측한다.
- 비기능 요구사항(성능, 접근성, 지원 기기, 보안, 데이터 보관)은 "해당 없음"이라도 칸을 채운다.

## 산출물 (프로젝트 `docs/` 폴더에 마크다운으로)
| 파일 | 내용 |
|---|---|
| `docs/prd.md` | 유형, 문제·대상·가치, 대안 비교, 가정과 위험, 성공 지표, 기능 요구사항, 비기능 요구사항, 개인정보, 범위 밖, 결정 기록·열린 질문 |
| `docs/user-stories.md` | "~로서, ~하고 싶다, 왜냐하면 ~" 유저 스토리 + 수용 기준 + 주요 사용 시나리오·예외 흐름 |
| `docs/screens.md` | 화면 목록, 화면별 상태, 화면 간 이동 흐름(Mermaid 흐름도) |
| `docs/mockups/*.html` | 주요 화면의 HTML 목업. 브라우저로 바로 열어 볼 수 있게, 모바일 폭 기준 |
| `docs/mvp.md` | MVP 범위와 우선순위(Must / Should / Later), 검증할 가정, 단계별 계획·출시 계획 |
| `docs/research/` | (사전 조사를 했다면) 페르소나 사양·응답·`hypotheses.md`·실제 인터뷰 질문지 |

- 플랫폼은 기본적으로 **반응형 모바일 웹 + 모바일 앱**이다. 설계는 폰 화면을 기준으로 한다(목업 폭 360~390px). 앱 전용 요소(푸시, 접근권한, 스토어 심사)는 PRD에 따로 적는다.
- 목업은 디자인 완성도보다 **화면 구성과 흐름 확인**이 목적이다. 단일 HTML 파일로, 외부 의존성은 최소로. 핵심 화면은 오류·빈 상태 하나씩도 만든다.
- 만든 뒤에는 내장 브라우저로 목업을 열어 모바일 폭에서 확인한다.

## AI 기능이 들어갈 때
읽을 것: `references/ai-features.md`
- AI가 맡는 부분과 일반 로직이 맡는 부분을 나눠 적는다. 규칙으로 되는 일은 AI에 맡기지 않는다.
- AI 응답이 틀리거나 느리거나 실패할 때 사용자에게 어떻게 보일지 정한다. 틀린 답의 피해가 큰 기능은 사람 확인 단계를 둔다.
- 품질 기준을 평가 예시 20~50개로 정하고(입력·기대 출력·합격 기준), 요청당 비용 상한을 적는다.

## 검토와 넘기기
읽을 것: `references/review-checklist.md` (기획 검토 요청을 받았을 때, 완료 전 자체 점검 때)
- PRD에 **결정 기록**(무엇을 왜 정했는지, 버린 대안)과 **열린 질문**(누가 언제까지)을 둔다. 개발·디자인은 이것으로 맥락을 받는다.
- 확정되면 `ux-ui-design` 스킬로 `docs/DESIGN.md`(디자인 기준)를 만들고, `frontend`, `backend`, `database` 스킬 기준으로 기술 구성을 제안한다. 넘길 때 Must 스토리·수용 기준·화면 상태·비기능 요구사항이 빠진 곳이 없는지 확인한다.

## 흔한 실수
- 해결책부터 정하고 문제를 끼워 맞춘다 → 1단계 문제 진술에서 해결책 단어를 뺀다.
- "모두를 위한 서비스" → 우선 타깃이 없으면 화면·문구·지표가 다 흐려진다.
- 경쟁 조사가 기능 비교표로 끝난다 → 범용 AI·비소비 대안과의 비교, "그들이 버린 사용자"가 빠진다.
- 지표를 출시 후에 정한다 → 측정 이벤트가 구현에 안 들어가 나중에 못 잰다.
- 가상 사용자·지인 칭찬("쓰겠다")을 수요 근거로 쓴다.
- 데모에 출시 서비스 절차를 다 적용해 시간을 쓴다 / 출시 서비스에서 법규 점검을 생략한다.

## 완료 기준
- [ ] PRD 맨 위에 유형이 있고, 0절 표에서 그 유형에 필수인 단계를 했다(생략한 단계는 이유를 적었다).
- [ ] PRD, 유저 스토리, 화면 흐름, 목업, MVP 문서가 `docs/`에 있다(연구 데모는 0절 표 기준).
- [ ] 문제 진술에 해결책 단어가 없고, 우선 타깃과 현재 대안이 적혀 있다.
- [ ] 경쟁·대안 조사에 범용 AI 대체 가능성 판단과 출처가 있다.
- [ ] 성공 지표에 정의·기준선(또는 `[가정]`)·목표·측정 이벤트가 있고, 가드레일과 중단 기준이 있다(데모는 시연 성공 기준).
- [ ] Must 스토리마다 수용 기준이 있고, 핵심 화면의 빈·로딩·오류 상태가 정해져 있다.
- [ ] 개인정보 수집 항목표가 있고, 법적 판단이 필요한 항목은 `[확인 필요]`로 표시했다.
- [ ] `[가정]` 표시가 남아 있으면 나에게 확인받았다. 범위·대상·고위험(법규·비용) 가정은 하나씩, 나머지(문구·목표 수치 등)는 목록으로 한 번에 보여 주고 검증 시점을 함께 적는다.
- [ ] 목업을 브라우저에서 모바일 폭으로 열어 확인했다.
- [ ] `references/review-checklist.md`로 자체 점검했다.
