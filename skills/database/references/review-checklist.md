# DB 변경 리뷰 체크리스트

> 언제 읽나: 스키마·마이그레이션·쿼리 변경을 리뷰할 때(직접 만든 것 포함), verifier에게 검증을 맡길 때 브리핑에 붙인다.
> 표기: **[필수]** 모든 경우 / **[출시]** 실제 사용자가 있는 서비스일 때. 해당 없는 항목은 "해당 없음"으로 표시하고 넘어간다.

## A. 스키마
- [ ] [필수] 모든 테이블에 PK, `created_at`/`updated_at`(timestamptz), `updated_at` 갱신 방식(트리거 또는 ORM 훅) 하나로 통일
- [ ] [필수] 키 전략이 기준에 맞다(내부 → bigint identity, 외부 노출·클라이언트 생성 → UUID v7). `serial`·자연키 PK 없음
- [ ] [필수] 필요한 곳에 NOT NULL·UNIQUE·FK·CHECK. 앱의 "조회 후 삽입" 중복 방지에 의존하지 않는다
- [ ] [필수] FK 컬럼(자식 쪽)에 인덱스가 있다
- [ ] [필수] `ON DELETE CASCADE`는 구성 요소 관계에만. 사용자·결제·감사 기록에 CASCADE가 퍼지지 않는다
- [ ] [필수] 시각 `timestamptz`, 돈 `numeric`/정수 최소 단위, 상태값은 CHECK 또는 참조 테이블(바뀔 수 있는 값에 ENUM 아님)
- [ ] [필수] JSONB 컬럼마다 "왜 컬럼이 아닌가"에 답할 수 있다
- [ ] [필수] 소프트 삭제를 쓴다면: 부분 unique 인덱스, 기본 필터, 파기 정책이 있다
- [ ] [출시] 다중 테넌트: 모든 테넌트 데이터 테이블에 `tenant_id`, 인덱스·unique 선두에 `tenant_id`, RLS 또는 강제 필터

## B. 마이그레이션
- [ ] [필수] 스키마 변경이 마이그레이션 파일로 있다(직접 ALTER·`push` 없음 — 로컬 포함)
- [ ] [필수] 자동 생성 파일을 사람이 읽었다: 이름 변경이 drop+add로 잡히지 않았는지, 빠진 기본값·제약이 없는지
- [ ] [필수] 로컬에서 `upgrade → downgrade → upgrade`를 실제 실행했다. 데이터 파괴적 down은 그 사실을 주석으로 적었다
- [ ] [필수] 이미 적용된 마이그레이션 파일을 수정하지 않았다
- [ ] [출시] 큰 테이블 작업이 `migrations.md` 2절 기준으로 안전한 방법을 쓴다(CONCURRENTLY, NOT VALID→VALIDATE, 휘발성 DEFAULT 회피, 타입 변경은 expand/contract)
- [ ] [출시] DDL에 `lock_timeout`이 있다
- [ ] [출시] 구버전 코드와 호환된다(컬럼 삭제·이름 변경은 코드 배포 후 다음 단계로)
- [ ] [출시] 백필은 별도 스크립트, 배치·멱등·재개 가능
- [ ] [필수] 운영 적용 전 사용자 확인을 받았다(변경 내용, 영향 행 수, 예상 락·시간, 백업 시점)

## C. 쿼리·성능
- [ ] [필수] 모든 값이 파라미터 바인딩. 동적 식별자는 허용 목록
- [ ] [필수] 목록 API에 N+1이 없다(SQL 로그로 요청당 쿼리 수 확인)
- [ ] [필수] 큰/커질 목록은 keyset 페이지네이션, 정렬 키가 유일(`, id` 포함)
- [ ] [필수] 새 WHERE/ORDER BY 패턴에 맞는 인덱스가 있거나, 없어도 되는 이유(작은 테이블)가 있다
- [ ] [출시] 핫패스 쿼리를 운영 규모 데이터에서 `EXPLAIN (ANALYZE, BUFFERS)`로 확인했다
- [ ] [필수] `SELECT *`로 큰 컬럼(벡터·긴 텍스트·JSONB)을 목록에서 읽지 않는다
- [ ] [출시] 앱 역할에 `statement_timeout`, `idle_in_transaction_session_timeout`

## D. 트랜잭션·동시성
- [ ] [필수] 트랜잭션 안에 외부 API·LLM·파일 업로드 호출이 없다
- [ ] [필수] 재고·잔액·카운터는 원자적 UPDATE 또는 락/낙관적 버전으로 처리(읽고-계산하고-쓰기 없음)
- [ ] [필수] 중복 요청 가능 지점(결제·주문 생성)에 멱등성 키 + unique
- [ ] [출시] 여러 행 잠금 순서가 일정(ID 오름차순). `40001`/`40P01` 재시도가 필요한 곳에 있다
- [ ] [출시] PgBouncer transaction 모드라면 세션 `SET`·세션 advisory lock·`LISTEN`을 쓰지 않는다

## E. pgvector (해당 시)
- [ ] [필수] 임베딩 모델 이름(버전 포함)·차원이 저장·고정돼 있다
- [ ] [필수] 인덱스 opclass와 쿼리 연산자가 일치(`vector_cosine_ops` ↔ `<=>`)
- [ ] [필수] 필터 + 벡터 검색에서 결과 수가 LIMIT보다 적어지는 문제를 처리했다(iterative scan, 부분 인덱스, 정확 검색 중 택1)
- [ ] [출시] 근사 인덱스의 recall을 샘플 쿼리로 측정했다
- [ ] [출시] 다중 테넌트 벡터 검색에도 테넌트 격리가 적용된다
- [ ] [필수] 문서 삭제 시 청크·임베딩도 삭제된다

## F. 보안·개인정보
- [ ] [필수] 비밀번호는 해시만, 비밀값(DB 비밀번호·암호화 키)이 코드·마이그레이션·로그에 없다
- [ ] [필수] 새 개인정보 컬럼마다 수집 이유·보존 기간을 `docs/database.md`에 적었다
- [ ] [필수] 민감정보(고유식별정보·금융·건강) 암호화를 검토했고 결론을 기록했다
- [ ] [필수] 시드·테스트 데이터에 실제 개인정보 없음
- [ ] [출시] 앱은 superuser·소유자가 아닌 최소 권한 역할로 접속, DB 포트 비공개
- [ ] [출시] 보존 기간 경과 데이터 자동 파기 작업이 있다(복사본·임베딩·백업 범위 포함)

## G. 운영 (출시 서비스)
- [ ] 백업이 자동으로 돌고, 다른 장소에 사본이 있고, 최근에 **복원 리허설**을 했다(RPO/RTO 기록)
- [ ] Docker 볼륨 경로가 이미지 버전에 맞다(PG18+: `/var/lib/postgresql`)
- [ ] `pg_stat_statements`, 연결 수, 오래된 트랜잭션, 디스크, 백업 성공 여부를 볼 수 있다
- [ ] 큰 쓰기 테이블의 autovacuum 설정을 점검했다
