# 데이터베이스 매뉴얼

> **팀으로 진행:** 여러 단계이거나 검증이 중요한 일은 `team-orchestration` 스킬의 "개발" 팀 구성(scout·builder·expert·verifier)으로 나눠 맡긴다. 각 팀원은 이 매뉴얼을 따른다.

## 기본 스택
- **DB**: PostgreSQL. 로컬과 운영 모두 Docker로 띄운다.
- **벡터 검색**: pgvector(PostgreSQL 확장). 별도 벡터 DB는 규모상 꼭 필요할 때만 제안한다.
- **ORM·마이그레이션**: 백엔드 스택에 맞춘다.
  - Python(FastAPI) → SQLAlchemy + Alembic
  - TypeScript(Next.js) → Drizzle 또는 Prisma

## 기본 규칙
- **스키마는 마이그레이션으로만 바꾼다.** DB에 직접 `ALTER`하지 않고, 마이그레이션 파일을 만들어 기록한다. 되돌리는 방법(down)도 확인한다.
- **운영 DB는 바꾸기 전에 묻는다.** 데이터 삭제·수정, 스키마 변경, 마이그레이션 적용 전에 무엇이 바뀌는지 보여 주고 확인받는다. 되돌리기 어려운 변경은 백업부터 제안한다.
- **개인정보 보호.**
  - 필요한 개인정보만 저장한다.
  - 비밀번호는 해시로만 저장한다.
  - 민감 정보(연락처, 주민번호 등)는 암호화를 검토한다.
  - 로그나 테스트 데이터에 실제 개인정보를 넣지 않는다.
- **스키마 문서.** `docs/database.md`에 테이블 설명과 ERD(Mermaid `erDiagram`)를 두고, 스키마가 바뀔 때마다 함께 고친다.

## 설계 원칙
- 모든 테이블에 기본키, `created_at`, `updated_at`을 둔다.
- 자주 조회하는 컬럼과 외래키에는 인덱스를 검토한다.
- 데이터 무결성은 DB 제약조건(NOT NULL, UNIQUE, FK)으로 지킨다.

## 완료 기준
- [ ] 스키마 변경이 마이그레이션 파일로 남아 있고, 로컬에서 적용·되돌리기를 실제로 해 봤다.
- [ ] 운영 DB 변경은 내 확인을 받았다.
- [ ] 개인정보 저장 방식이 위 규칙에 맞다.
- [ ] `docs/database.md`의 ERD가 최신이다.
